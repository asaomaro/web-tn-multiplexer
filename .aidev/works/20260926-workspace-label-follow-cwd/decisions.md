# 決定記録

## D1: profile は full、research を挟む（着手時の判定）

- 背景: backlog の 1 項目（`.aidev/backlog/product-roadmap.md:345`）を autonomous で起こした。自動の名前（SessionService）・git の監視（GitInfoPoller）・
  pane のいまの場所（AgentMonitor が更新する `Pane.cwd`）・復元の 3 か所以上にまたがり、振る舞いを変える。
- 決定: `profile: full`。requirements の後に research を挟む（protocol「4.5」の「未検証の既存挙動に依存する」「影響が横断的」に当たる）。
- 理由 / 代替案: light は「振る舞いを変えない小規模」が条件で当たらない。research を省くと、`Pane.cwd` がいつ・どの頻度で更新されるか、
  名前の決め直しとの競合（名前変更の世代 `labelGen`）を確かめずに design を書くことになる。
- 影響: research.md を作る。

## D2: 「根の pane」は id で覚えず、そのときの画面の並びの先頭の pane を使う（herdr との違い）

- 背景: herdr は tab ごとに `root_pane` を覚え、入れ替え・移動をしても同じ pane を根とし、閉じたときだけ残りの先頭に代える
  （`src/workspace/tab.rs:459-524`）。本製品の `Tab` には根の pane の項目が無い（`packages/protocol/src/model.ts` の `Tab`）。
- 決定: 最初の tab の、分割の木を左・上から順にたどった先頭の pane（`LayoutTree.leaves(layout)[0]`）を使う。requirements の「非機能要件 / 制約」に
  herdr との違いとして書き、対応表にも書く。
- 理由 / 代替案: 根の pane を覚えるには protocol の `Tab` と `session.json` に項目を足し、分割・入れ替え・移動・復元のすべての経路で保つ必要がある。
  違いが出るのは入れ替え・端への移動で左上の pane が代わったときだけで、そのときも「左上の pane の場所」という見た目どおりの規則になる。
- 影響: design で「最初の pane」を 1 か所の関数にする。

## D3: requirements の独立点検は 2 ラウンドで打ち切った

- 背景: ラウンド 1 で 7 件、ラウンド 2 で 2 件（AC15 と AC11 の食い違い・OSC 7 が無いときの基準の食い違い）。上限は 2。
- 決定: ラウンド 2 の 2 件を最小の差分で直し、3 ラウンド目は行わずに承認へ進む。残った疑問があれば design の点検・review に委ねる。
- 理由: 上限（maxDocCheckRounds=2）に達した。2 件とも文言の食い違いで、直し方が指摘に書かれている。
- 影響: なし。

## D4: design の独立点検は 2 ラウンドで打ち切った

- 背景: ラウンド 1 で 5 件、ラウンド 2 で 3 件（名前を空にした待ちの再試行の上限を超えたときの扱い・`degraded` の書き方の不揃い・出所の書き方）。上限は 2。
- 決定: ラウンド 2 の 3 件を最小の差分で直し、承認へ進む。再試行の上限を超えたときは「名前を入れず `autoLabel` だけ立てて監視に任せる」にした。
- 理由: 上限に達した。古い場所の名前で上書きしないこと（AC6）を優先し、名前が決まるのは次の周期（最長 5 秒）に遅れることを受け入れる。
- 影響: 実装と review で確かめる。

## D5: tasks の独立点検は 2 ラウンドで打ち切った

- 背景: ラウンド 1 で 7 件、ラウンド 2 で 2 件（GitInfoPoller 側の AC11 のテスト・AC5 のイベントの種類ごとのテストと負の確認）。上限は 2。
- 決定: ラウンド 2 の 2 件をテスト方針に足して承認へ進む。
- 理由: 上限に達した。どちらもテスト方針の書き足しで、直し方が指摘に書かれている。
- 影響: coding（T2）のテストに反映する。

## D6: T1 の点検で見つかった、単体で捕まえられない変異（受け入れ）

- 背景: T1 の点検（ラウンド 1）で、(1) `degraded` を待ち終えた時点の `labelLookupsStuck` で判定する変異、(2) reject を degraded に含めない変異、
  (3) 閉じた workspace の `labelCwd.delete` を消す変異が、テストを通ると指摘された。
- 決定: (1) は「上限超えの直後、待っている側が再開する前に止まっていた問い合わせが返る」順序がマイクロタスクの順序に依り、単体で確実に作れないので
  テストでは捕まえない（実装は design D3 どおりで、読解で確かめる）。(2) は `autoWorkspaceLabel` が投げない作り（`workspaceLabel.ts` の注記）で、reject を起こすには
  deps の path を壊す必要があり、壊すと代わりの `folderLabelOf` も同じ path で投げるので観測できない。防御として残す。(3) は id が使い回されず、害は Map に
  1 件残るだけなので許容する。
- 理由 / 代替案: テストのために `withTimeout` の順序へ時計を差し込む口を足すのは、製品のコードに試験専用の形を増やす。
- 影響: review で読解の対象にする。

## D7: `pane.closed`・`tab.closed` の購読は念のために残す（テストでは見分けられない）

- 背景: T2 の点検で、購読の対象から `pane.closed` か `tab.closed` を 1 種類ずつ外しても、AC5 のテストが通ると指摘された。閉じる操作は、その後に
  必ず `layout.updated` か `workspace.updated` も出す（`SessionService.closePane`・`closeTab`）ので、後のイベントで気づける。
- 決定: 2 種類は購読に残す（design D4 のまま）。AC5 のテストは「閉じる操作に追従する」ことを確かめるものとし、この 2 種類を外す変異を捕まえられない
  理由をここと test-result.md に残す。
- 理由 / 代替案: 外すと、将来閉じる操作が後のイベントを出さなくなったときに追従が周期（5 秒）まで遅れる。購読の費用はメモリの比較だけ。
- 影響: test-result.md の負の確認に明記する。

## D8: 保存の tab の並びを、並べ替えた順にした（tasks に無かった変更）

- 背景: またぐ点検（cross）で、保存（`composeServer.ts` の `toSessionFileData`）が tab を作った順で書くため、並べ替えた後に再起動すると復元の最初の tab が
  並べ替える前のものになり、「止める前にいた場所から決め直す」（AC8・docs）が成り立たないと指摘された。以前からの欠落（tab の並びが再起動で戻る）でもある。
- 決定: `ws.tabIds` の順で保存する。統合テストを 1 本足す。保存の形（項目）は変えない（AC14）。
- 理由 / 代替案: 既知の制約として書く案は、直す差分が 2 行で済むので退けた。
- 影響: tasks.md に T5 として足した。

## D9: test 工程の 1 回目の失敗は、テストの作りの直しとして test 工程の中で直した（coding へ差し戻さない）

- 背景: 一式の 1 回目で、T5 で足した統合テストが 1 件落ちた（`expected [ 't2' ] to deeply equal [ 't3', 't2' ]`。新しい tab が保存に無い）。単独では 3 回とも通った。
- 決定: 製品の欠陥ではなく、既定のシェルを起動するテストが負荷の下で揺れたものと判断し、test 工程で「待つだけのシェル」で起動する形に直した（既存の
  「引き継ぐ」の統合テストと同じ作り）。負の確認（M32）を取り直して落ちることを確かめた。生の出力は test-result.md の「失敗の証跡」。
- 理由 / 代替案: 差し戻すと coding→test を 1 往復するが、変わるのはテストの起動するシェルだけ。
- 影響: review で確かめる。

## D10: worktree の一覧・作成・削除も、いまの場所のリポジトリで行う（requirements の対象外を移した）

- 背景: review ラウンド 1（should）。worktree のメニューを出すかは `ws.git`（この work でいまの場所から取る）で決めるが、`WorktreeService` は開いた場所で git を
  走らせていた。git の外で開いてリポジトリへ `cd` すると項目が出て選ぶと失敗し、別のリポジトリへ移ると元のリポジトリの worktree を並べる。
- 決定: `WorktreeService.cwdOf` を `session.identityCwdOf` にする。requirements の対象外と AC9 から「worktree の一覧」を外し、対応表・docs に書く。
  既に開いているかの判定（web の `w.cwd === path`）・新しい tab の代わり・保存の `cwd` は開いた場所のまま。
- 理由 / 代替案: herdr も worktree の操作は追従した git の情報（`ws.git_space()` か `resolved_identity_cwd_from`）から取る（`src/app/api/worktrees.rs:323-326`・`:380-383`。
  主エージェントが直読）。退けた案：メニューの出し分けを開いた場所の判定に揃える——サイドバーが B のブランチを出しているのに A の worktree を並べる食い違いが残る。
- 影響: T6。

## D11: リンクを含む論理パスと実パスが同じディレクトリなら、名前を決め直さない

- 背景: review ラウンド 1（should）。作成時は論理パス（`resolvedCwd`）を記録するが、監視は `/proc/<pid>/cwd` の実パスを `Pane.cwd` に入れるので、リンクを含む場所では
  `cd` しなくても約 1 秒後に名前が実パスのフォルダ名に変わる。design の「同じ場所なら同じ文字列」が成り立たない。
- 決定: `followedLabel` は、決めた場所と新しい場所をリンクを解決して比べ（`WorkspaceLabelDeps.realpath`。上限つき・fs が詰まっている間は比べない）、同じなら
  いまの名前のまま場所だけ記録する。git の情報はいまの場所で取り直すだけなので変えない（同じリポジトリなので同じ値）。
- 理由 / 代替案: 記録の前に realpath を取る案は、作成・名前変更・復元のすべてで待ちが増え、表示の名前も実パス側になる。比べるのは場所が変わったと見えたときだけで済む。
- 影響: T7。

## D12: T6・T7 の点検を 1 回の委譲にまとめた（protocol-check の「1 委譲 = 1 タスク」からの逸脱）

- 背景: review の差し戻しで足した T6・T7 は、どちらも数行の差分だった。
- 決定: 1 つのコンテキストに両方を渡し、返却をタスクごとのブロックに分けさせて、`taskcheck report` はタスクごとに打った。
- 理由: 時間の節約。記録上は `task_checks` が 2 件、コンテキストは 1 つになる（「1 コンテキストが何件拾ったか」は T6 3 件・T7 2 件と review.md に分けて残した）。
- 影響: insights で点検の効果を数えるときの注意点。

## D13: review ラウンド 2 の nit 2 件は許容した

- 背景: (1) 名前を決める処理が詰まった・上限を超えたときに `labelCwd` を消すため、その後はリンクを含む論理パスと実パスの比較（D11）を通らず実パスの名前になる。
  (2) `WorktreeService.cwdOf` がいまの場所が使えるかを上限なしで確かめる。
- 決定: どちらも許容し、backlog にも起票しない。
- 理由: (1) は止まった・遅い fs とリンクを含む場所が重なったときだけで、そのときの名前もそのディレクトリの実の名前として誤りではない。(2) は新しく開く場所
  （`resolveNewCwd` の `isUsableDir`）と同じ扱いで、応答しない fs の上では作成も同じく戻らない。
- 影響: なし。
