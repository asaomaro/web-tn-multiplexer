# 要件: D&D による pane の分割・分割解除

紐づく charter ゴール: なし（`.aidev/charter.md` 未導入）。

`.aidev/backlog/product-roadmap.md` の既存項目「D&D による pane の分割 / 分割解除 / 移動（Web 固有の
操作）」（出典: `.aidev/works/20260918-web-terminal-multiplexer/requirements.md`）のうち、
**「分割」「分割解除」を対応する**。「移動」（別 tab・別 workspace への D&D 移動）は、既に
`20260923-pane-name-dnd-swap` が「同一 tab 内の入れ替え」を対応済みなのと同じ理由で、
スコープを絞るため本 work では対象外とし、backlog に新しい行として残す（決定は decisions.md D1）。

## 背景 / 課題

`20260923-pane-name-dnd-swap` で、pane の名前ラベルをドラッグして**同一 tab 内の既存 pane 同士を
入れ替える**操作を実装した。しかし herdr には無い「Web ならではの直接操作」として当初想定していた
「ドラッグで分割する」「ドラッグで分割を解除する」は、その work の対象外として明示的に backlog へ
残されたままになっている（`.aidev/works/20260923-pane-name-dnd-swap/requirements.md`「対象外」）。

現状、pane を分割するにはキーバインド（`prefix+…`。design 「振る舞いの詳細」）または pane 枠のボタンで
行うしかなく、「既にある pane を、別の pane の隣へドラッグしてそこに割り込ませる」「不要になった
分割をドラッグで畳む」という、マウス操作主体の直感的な組み替えができない。

## 目的 / ゴール

- 利用者が、既存の pane（名前ラベルを摘まむ）を**別の pane の縁（上下左右）**へドラッグ＆ドロップする
  ことで、ドロップ先の pane がその方向に分割され、ドラッグした pane がその新しい区画へ移り、
  元あった場所の split は自動的に畳まれて兄弟がスペースを引き継いでいる状態。
- 利用者が、既存の pane を**別の pane の中央**へドラッグ＆ドロップすることで、ドロップ先の pane が
  閉じられ、ドラッグした pane がその位置（とその区画が占めていたスペース）を引き継ぐ状態
  （分割の「解除」——2つの pane が1つに畳まれる）。
- 既存のキーボードによる分割・分割解除相当（`pane.split`・`pane.close`）は変わらず使える状態
  （マウス操作を追加するもので、キーボードでの操作を置き換えない）。
- `20260923-pane-name-dnd-swap` で確立した「名前ラベルをドラッグする」操作の対象を広げるだけで、
  利用者からは1つの一貫したドラッグ操作に見える状態（ドロップ先のどこに落とすかで「分割」
  「分割解除」のどちらになるかが決まる。**decisions.md D4**：縁・中央の2ゾーンで両方を表現する
  ため、`20260923-pane-name-dnd-swap` の「ドロップ先を問わず入れ替え」という既存の挙動は、
  この新しいゾーン方式に置き換わる——両立できない〔安全な入れ替えと、プロセスを実際に終了させる
  分割解除を、同じ「pane を pane へドロップする」操作の中で両方とも常時到達可能にはできない〕）。

## ユーザーストーリー

- US1: 複数 pane を並べて作業する利用者として、既にある pane を別の pane の縁へドラッグするだけで、
  そこに新しい分割を作ってその pane を移したい。なぜなら、キーバインドでの分割は「今フォーカスして
  いる pane の隣に**新しい** pane を作る」操作しかできず、「既存の pane をレイアウトの別の場所へ
  組み替える」には一度閉じて作り直すしかなく、作業内容（動いているプロセス・スクロールバック）を
  失ってしまうから。（受け入れ: AC1〜AC4, AC8〜AC11, AC-I1〜AC-I5）
- US2: 分割しすぎて狭くなった画面を整理したい利用者として、不要になった pane を隣の pane へドラッグ
  して重ねるだけで、その分割を畳んで隣の pane にスペースを譲りたい。なぜなら、pane を閉じるための
  キーバインド・右クリックメニューは対象を選んでから実行する2段階の操作で、隣の pane へ「渡す」
  という直感的な操作ではないから。（受け入れ: AC5〜AC11, AC-I1〜AC-I5）

## スコープ

### 対象

- `PaneFrame.vue` の既存のドラッグ機構（`onNamePointerDown`/`onNamePointerMove`/`onNamePointerUp`。
  `20260923-pane-name-dnd-swap`）を拡張し、ドロップ先の pane 内のどこ（縁 or 中央）へ落としたかを
  判定する。
- ドロップ先が**縁**（上下左右のどれか）: ドロップ先の pane をその方向に分割し、ドラッグした pane を
  新しい区画へ移す（新しい pane は作らない。既存の pane がレイアウト内で位置を変える）。
  ドラッグした pane の元の位置は、既存の `pane.close`/`LayoutTree.remove` と同じ「兄弟を昇格する」
  処理で畳まれる。
- ドロップ先が**中央**: ドロップ先の pane を閉じ、ドラッグした pane がその領域（親の split が畳まれた
  結果のスペース）を占める。ドラッグ元の元の位置も同様に畳まれる。
- ドラッグ中の視覚的フィードバック: ホバー中の pane のどの縁/中央に反応しているかが分かる表示
  （既存の「ドロップ先候補が分かる」表示の拡張）。
- 同一 tab 内の操作に限る（`20260923-pane-name-dnd-swap` と同じ前提）。
- ドロップ操作の失敗時（範囲外・同じ pane 自身へドロップ・無効な対象）は何も起きない（現状維持）。
- protocol 層の新規/拡張 RPC（サーバ側で「既存の pane を指定方向に分割し、その pane を移す」
  「既存の pane をドロップ先へ吸収させて片方を閉じる」を実現する手段。設計は design で確定する）。

### 対象外

- **別 tab・別 workspace への pane の移動**（同じ backlog 項目のうち「移動」の残り。tab バーや
  サイドバーへドロップする経路。decisions.md D1 で本 work から切り出し、新しい backlog 項目として
  残す）。
- タッチ操作でのドラッグ（`PaneFrame` の名前ドラッグはデスクトップ限定〔`enabled` prop〕のまま。
  `20260923-pane-name-dnd-swap` と同じ理由）。
- 名前が無い pane（`paneAgentNameVisible` が off、または名前を導出できない）でのドラッグ操作
  （`20260923-pane-name-dnd-swap` と同じ制約を引き継ぐ）。
- 3つ以上の pane を同時に組み替える複合操作（1回のドラッグ＆ドロップは常に「ドラッグ元1つ・
  ドロップ先1つ」の関係に限る）。
- ドラッグでの split 比率（`ratio`）の指定（新しく出来る分割は既定の 0.5 固定。細かい比率調整は
  既存の境界ドラッグ〔リサイズ〕に任せる）。

## 機能要件

- pane の名前ラベルをドラッグし、別の pane の**縁**（上下左右のどれか）にドロップすると、
  ドロップ先の pane がその方向へ分割され、ドラッグした pane が新しい区画に入る。
- pane の名前ラベルをドラッグし、別の pane の**中央**にドロップすると、ドロップ先の pane が閉じ、
  ドラッグした pane がそのスペースを引き継ぐ。
- どちらの操作でも、ドラッグした pane が元々あった場所の分割は自動的に畳まれ、その兄弟が
  スペースを引き継ぐ（既存の `pane.close` と同じ挙動）。
- ドラッグ中、ホバーしている pane 上のどの領域（上/下/左/右/中央）に反応しているかを視覚的に示す。
- 分割・分割解除いずれの結果でも、フォーカスはドラッグした pane（移動・存続した方）に残る。
- 既存のキーバインドによる分割（`prefix+…`）・pane を閉じる操作は、この work の変更後も従来どおり
  動作する（回帰なし）。`pane.swap_with`（`SessionModel`/`SessionService`。RPC そのもの）も変更・
  削除しない——ただし `PaneFrame.vue` の名前ラベルドラッグからの呼び出し（`swapPanesByDrag`）は、
  縁/中央のゾーン方式に置き換わるため対象外（decisions.md D4）。

## 非機能要件 / 制約

- 複数クライアントが同じ tab を見ている場合、分割・分割解除の結果はサーバから配られる
  `tab.updated`（または既存の layout 更新イベント）で全クライアントに反映される（既存の
  レイアウト変更イベントの仕組みをそのまま使う。design で確定）。
- パフォーマンス上の新しい制約は無い（既存の `pane.split`/`pane.close`/`pane.swap_with` と
  同程度の操作頻度・レイテンシを想定）。

## 相互作用の受け入れ基準

利用者が操作する部品（pane のドラッグ＆ドロップ）を拡張するため記載する。

- [ ] AC-I1 開く / 閉じる: ドラッグは名前ラベルの pointerdown→閾値超えの pointermove で始まり
  （`20260923-pane-name-dnd-swap` と同じ 6px 閾値）、pointerup で終わる。ドロップ先が無効・
  範囲外なら何も起きず、レイアウトは元のまま。
- [ ] AC-I2 確定 / 取り消し: pointerup で有効なドロップ先（縁 or 中央）の上にいれば確定する。
  ドラッグ中に Esc を押すとドラッグを取り消し、レイアウトは元のまま（`20260923-pane-name-dnd-swap`
  の `onEscapeDuringDrag` と同じ経路）。
- [ ] AC-I3 キーボードだけで完結するか: この操作自体はマウス/ポインタ操作前提（`20260923-pane-name-dnd-swap`
  と同じ位置づけ）。同じ結果（分割・分割解除）は既存のキーバインド・ボタン操作でキーボードだけでも
  到達できる状態を維持する（この work が退行させない）。
- [ ] AC-I4 フォーカスの行き先: ドロップ確定後、ドラッグした pane（分割で移った pane・分割解除で
  生き残った pane）にフォーカスが残る。
- [ ] AC-I5 既存の操作を妨げないか: 名前ラベル以外の pane 枠内のクリック・既存のリサイズ（境界の
  ドラッグ）・既存のキーバインド操作の経路は変更しない。

## 完了条件 (受け入れ基準)

- [ ] AC1: pane の名前ラベルをドラッグし、別の pane の上端/下端/左端/右端にドロップすると、
  ドロップ先の pane がその方向に分割され、ドラッグした pane が新しい区画に入る。
- [ ] AC2: AC1 の分割で、ドラッグした pane が元あった場所の分割は畳まれ、兄弟がスペースを引き継ぐ。
- [ ] AC3: AC1 の分割後、既存のリサイズ操作でその新しい分割の境界を動かせる（既存の split と
  同等に扱われている）。
- [ ] AC4: ドラッグ中、ホバー中の pane の縁のどこに反応しているかが視覚的に分かる。
- [ ] AC5: pane の名前ラベルをドラッグし、別の pane の中央にドロップすると、ドロップ先の pane が
  閉じ、ドラッグした pane がそのスペースを引き継ぐ。
- [ ] AC6: AC5 の分割解除で、ドラッグした pane が元あった場所の分割も畳まれ、兄弟がスペースを
  引き継ぐ（両側で畳まれる）。
- [ ] AC7: AC5 でドロップ先の pane が閉じられたことで、その pane で動いていたプロセスが終了する
  （既存の `pane.close` と同じ挙動。データの引き継ぎは無い）。
- [ ] AC8: 分割・分割解除いずれの操作後も、フォーカスはドラッグした pane に残る。
- [ ] AC9: 同一 pane 自身へのドロップ・tab の外側へのドロップでは何も起きない（レイアウト不変）。
- [ ] AC10: 複数クライアントが同じ tab を開いているとき、一方の分割・分割解除操作がもう一方の
  画面にも反映される。
- [ ] AC11: 既存のキーバインドによる分割・pane を閉じる操作は、この work の変更後も従来どおり
  動作する。`pane.swap_with`（`SessionModel`/`SessionService`。RPC 自体・その単体テスト）も
  変更しない。名前ラベルドラッグから `swapPanesByDrag` を呼ぶ経路（`20260923-pane-name-dnd-swap`）
  は、縁/中央のゾーン方式（分割・分割解除）に置き換わるため、この work以降は到達しなくなる
  ——これは意図した置き換えであり回帰ではない（decisions.md D4）。

## 未確定事項 / 確認したいこと

- ドロップ先の pane 内で「縁」と「中央」の境界（何 px・何 % を縁とみなすか）の具体的な閾値は
  design で決める（VS Code のエディタ分割や類似の web ターミナル/IDE がどう決めているか、確立した
  パターンを design 前の research で確認する）。
- サーバ側の RPC 設計（既存の `pane.split`/`pane.close`/`pane.swap_with` を組み合わせて表現するか、
  新規の複合 RPC を1つ追加するか）は design で決める。
