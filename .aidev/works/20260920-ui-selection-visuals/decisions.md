# 決定記録

## D1: AC9・AC-I1・AC-I2・AC-I4・AC-I5 は coding ではなく test 工程で消化する

- 背景: この 5 つの受け入れ基準は「既存の振る舞いを壊していないこと」を求めるもので、
  design の「受け入れ基準との対応」でも**既存の単体テスト・既定の E2E の通過**をもって確認するとしている。
  対応するタスク T14 は「一式を走らせて結果を記録する」だけで、coding 工程で書く差分を持たない。
- 決定: **T14 は coding 工程では未チェックのまま承認してよい**（`aidev-30-tasks` 手順 6 の
  「coding ではなく test / deliver で消化する」に当たる）。消化は test 工程で行う。
- 理由 / 代替案: coding 中に毎回全 E2E（既定 60 件・約 4 分）を回すと刻みが粗くなる。
  各タスクの直後に回すのは**そのタスクが触るパッケージの単体テスト**までとし、
  一式は test 工程で 1 回通す。
- 影響: `aidev-40-coding` の「完了の目安（全タスクがチェック済み）」と形の上で食い違うので、この記録を証跡とする。

## D2: 着手前から失敗している E2E が 1 件ある（`mobile.spec.ts` の D105）

- 背景: この work に着手する前のコミット（`9db9e14`）で `pnpm -r test` を走らせたところ、
  単体テストは 1066 件すべて合格・typecheck も通ったが、**E2E は 59 passed / 1 failed** だった。
  落ちたのは `packages/e2e/src/specs/mobile.spec.ts:77`（D105：分割後に隠れた pane の PTY の大きさが変わらない）で、
  `rows` が期待 41 に対し 38。単独で再実行しても同じ場所で落ちるので、一時的な揺れではなく**この環境で再現する失敗**。
- **観測をまとめると（計 8 回）**:

  | 走らせ方 | コード | 結果 |
  |---|---|---|
  | E2E 一式 | 着手前（`9db9e14`） | **失敗**（`rows` 41 期待 → 38） |
  | この spec だけ | 着手前 | **失敗**（同じ） |
  | E2E 一式 | 実装後 | 合格（63/63） |
  | E2E 一式 | review ラウンド1 の修正後 | **失敗**（同じ `rows` 41 → 38） |
  | この spec の D105 だけ ×3 | 同上 | **3 回とも合格**（各 3〜4 秒） |

  → **単独では落ちず、一式で走らせたときだけ落ちる**。つまり恒常的な不具合でも純粋な偶然でもなく、
  **負荷でタイミングが変わると現れる競合**。着手前のコードでも一式では落ちているので、
  **この work が作ったものではない**。
- 決定: **この work では直さない**。上の観測をそのまま `test-result.md` に残し、backlog へ送る。
- 理由 / 代替案: (0) 不安定なテストの原因究明は、落ちる条件を先に突き止める作業で、見た目の修正とは別物。
  (1) この work の変更はモバイル（`MobileShell`）に届かない
  （`App.vue:41-43` のとおり `Sidebar` も `PaneFrame` の枠もデスクトップ側だけ）ので、因果が無い。
  (2) 原因は分割時の `client.view` の送信順（D105 の範囲）で、調べるには別の work の規模になる。
  (3) ここで直すとこの work の差分に無関係な変更が混ざり、review の範囲が読めなくなる。
- 影響: test 工程の合否は「一式が緑」で扱えるが、**不安定であること自体**を PR 本文の「既知の制約」に載せる。

## D3: `.sidebar-divider` の位置を変える（`right: -3px` → `right: 0`）

- 背景: 要望 2（横スクロールバーを出さない）の原因を調べたところ、原因は 2 つあった。
  1 つは 2 行目のテキストが縮まないこと、もう 1 つは**幅変更のつまみが containing block の外へ 3px はみ出している**こと
  （`Sidebar.vue:216-224`）。後者はテキストが 1 文字も無くても `scrollWidth` を 3px 広げる
  （独立点検が実測: `scrollWidth` 243 / `clientWidth` 240。つまみを消すと 240/240）。
- 決定: つまみを `right: 0` に寄せ、はみ出しを無くす。併せて `.sidebar` に `overflow-x: hidden` を足す。
- 理由 / 代替案: 代替は「判定対象を `.sidebar` から中の区画へ変える」だが、
  **スクロールバーが出る主体は `.sidebar`** なので、それでは要望そのものを満たしたか確かめられない。
  つまみのドラッグは移動量の差分で幅を決める（`Sidebar.vue:87` の `ev.clientX - dragStartX`）ので、
  位置を 3px ずらしても操作感は変わらない。
- 影響: 掴める帯が「境界をまたぐ 6px」から「内側の 6px」になる。
  `terminal-app.spec.ts:235`（折りたたみ）は `.sidebar` の幅を変えないので影響しない。
- **横断の点検が見つけた副作用（と、それを受け入れる理由）**: つまみは `position: absolute` なので
  通常フローの `.sidebar-row` より上に描かれ、**重なった範囲は行のクリック・ホバーを奪う**。
  以前は 6px のうち外側 3px が `.sidebar` の外にあり（スクロール位置 0 では見えず、当たり判定も届かない）、
  行から奪っていたのは実質 3px だった。内側へ寄せたことで **6px すべてが行と重なる**。
  それでもこの形を採るのは、(1) 以前は**掴める幅が実質 3px しかなく**、幅を変えるのが難しかった。
  内側へ寄せると宣言どおりの 6px が掴めるようになる。(2) 重なった範囲では
  `cursor: col-resize`（`Sidebar.vue` の `.sidebar-divider`）に変わるので、
  「ここは行ではなくつまみ」だと押す前に分かる。(3) 奪われるのは幅 240px の行の右端 6px（2.5%）で、
  行のどこを押しても同じ動作（workspace の切替）なので、押す場所を選べば済む。
  **この判断は「掴みやすさ」と「行の端 3px」を交換したもの**で、実測ではなく見立てなので、
  使ってみて押しにくければ戻す（そのときは `width: 3px` にすれば以前と同じ実質 3px に戻せる）。
