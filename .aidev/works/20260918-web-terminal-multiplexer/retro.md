## うまくいった点

- **タスク単位の独立点検（`aidev taskcheck`）が、review に届く前に 100 件を潰した**
  （01: 38 / 03: 31 / 05: 27 / 04: 4、点検したタスク 20 件）。同じ期間の review のラウンド指摘は must 13・should 33・nit 32。
  **点検で潰した 100 件のほうが多い**。とくに `--mode delegated`（別コンテキスト）にしたものは、自分では気づけなかった
  経路（ポインタ操作の入力・ログの氾濫・pid 名前空間・`Retry-After` の端の値）を継続的に拾った。
- **回帰テストに毎回「否定対照」を付けた**（修正前のコードに戻して落ちることを確認）。これで**無効なテストを 3 回検知した**——
  D98 の最初のテスト（修正前でも通る）・T24 の分割のテスト（条件付きの解除に戻しても通る）・T31 の入れ替えの前提。
  「テストが通った」ではなく「テストが効いている」ことを確かめる手順として、費用に見合った。
- **統合 test / 統合 review が、単体の review では原理的に見えない欠陥を多数捕まえた**：D88（イベントの取りこぼし）・
  D96（xterm.css の読み込み漏れ＝画面に何も映らない）・D97（焦点の遅れ）・D98（流量制御が一度も働いていない）・
  D100（zoom の解除）・D105（隠れた pane が 1×1）・統合 review の must 3 件（再接続で画面が止まる・fit していないモバイルに
  サイズ権限・窓の大きさに追従しない）。**分割したまま単体 review だけで着地していたら、どれも残っていた。**
- **決定の記録（D1〜D111）が、誤認の訂正を可能にした**。D96 に書いた「typecheck は見逃す」は誤りで、実際は `pnpm -s` が
  失敗時に何も出力しないことによる見落としだった。記録が残っていたので後から訂正でき、同じ落とし穴をメモリにも残せた。
- **実物のブラウザ・実物のサーバでの確認**。E2E の判定だけでなく、スクリーンショットの目視で D96 を発見した。
  実物の Claude Code / Codex を pane で起動しての確認も、判定ルールの検証に効いた。

## 課題 / 手戻り

- **再開 77 回・review の差し戻しが 01 で 7 回**。最大の原因は**上流の欠落**で、統合 review の差し戻し後に `aidev debug` へ
  委譲して言語化できた（`01-server-core/decisions.md` のデバッグ D1）：
  **「ブラウザがどのアドレス・ポート・名前でサーバに届き、どの Host/Origin を送り、証明書のどの名前と照合されるか」の
  モデルが design に無かった**。そのため表示も許可リストも「サーバ自身のインタフェース＋待ち受けポート」だけで作られ、
  WSL2 の NAT・リバースプロキシ・Tailscale・仮想ブリッジで一斉に破れた（D102）。
  → **design の段で「到達経路の表」（構成 × `--port` × `--origin` × 開く URL × 証明書の SAN）を書いていれば防げた**。
- **テストの「観測点」が利用者の見る場所とずれていた**。繰り返し同じ形で失敗した：
  - バイト列の往復だけを見て画面を見ていない → 端末が 1 文字も見えないまま E2E が緑（D96）。
  - テスト自身の WebSocket クライアントでイベントを待ってブラウザを操作 → ブラウザ側の反映前に進んで競合（D104・05 T13）。
  - テスト用クライアントが SNAPSHOT を出力として数えない → 購読前に済んだ出力を見落として間欠的に失敗（05 T16。
    04・統合の 2 ラウンドを「負荷のせい」と誤判断させた）。
  → 「**判定はブラウザ側の観測（描画・ブラウザが受けたフレーム）で行う**」を最初から規約にしていれば、3 件とも避けられた。
- **統合 review のラウンドが収束しなかった**（01 のラウンド 5 → 6 → 7）。毎ラウンド新しいレビュアー（別コンテキスト）が
  範囲を広げ、周辺の**以前からある**欠陥（`token reset` が動かない・不正 URL でログが氾濫・M6/M7 のマウス）を拾い続けた。
  価値のある発見だったが、**終わりの条件が無い**まま回っていた。ラウンド 7 で「前ラウンドの解消 ＋ 当該差分の must/should」に
  範囲を絞って初めて収束した。
- **AC17（性能）の合否が自動では決められない設計だった**。このサンドボックス（ソフトウェア GL・負荷あり）では
  大量出力中の 16 pane で p95 513ms（目標 50ms）。**最初から「実機で判断する」と決めておけば**、計測の往復（親の test を
  3 ラウンド消費）を減らせた。
- **記録の穴**：04 の coding の `start` 1 回漏れ（D111）。`aidev verify` の WARN で気づいたが、時間は復元できない。
- **条項（`.aidev/conventions/`）が 1 つも無かった**ため、review の指摘は**全 78 件が `[conv:-]`**。
  再発した類型（上の 2 つ）を横断で効かせる手段が無かった。

## 改善提案

### 製品 / コード（→ backlog）

backlog には既に 20 件（後続機能 10 件＋この work で見つけた残件 10 件）。この retro から追加するのは次の 3 件。

- E2E の観測点をブラウザ側にそろえる共通部品（`support/frames.ts` の CDP / 中継と `panes.ts` の `client.view` 観測を
  入口 1 つに整理し、spec がテスト用クライアントだけで合否を決められないようにする）。
- `pnpm` のスクリプトを「失敗が見える」形にする（`-s` の再帰実行は失敗時に何も出力しない。ルートの script か CI の
  呼び出しで出力と終了コードを必ず残す）。
- AC17 の実機計測の結果を反映する work（D98 の閾値 2MB / 256KB の見直しを含む）。

### PJ プロセス / 規約（→ `.aidev/conventions/` の条項）

`[conv:-]` が集中した 2 類型を条項として起こす（**id 付きの指摘が繰り返された事例は無い**——条項がそもそも存在しなかったので、
「規約はあるが守られていない」ではなく「規約の穴」と判別した）。

- **`e2e-observe-browser`**：E2E の合否は、利用者が見る場所（ブラウザの描画・ブラウザが受けたフレーム・DOM）で判定する。
  テスト自身の WebSocket クライアントは、前提を作るためと**サーバ側の状態**の確認にだけ使う。
  根拠：D96・05 の T13・05 の T16（いずれも `[conv:-]`）。
- **`regression-negative-control`**：回帰テストは、修正前のコードで**落ちること**を確かめてから採用する（確かめた出力を
  test-result.md に貼る）。根拠：D98・T24・T31 で無効なテストを 3 回検知。

### ハーネス自体（→ `aidev-*` への提案。適用は人間）

1. **`aidev-60-review`：ラウンド 2 以降の範囲を絞る規定を入れる**。
   現状「差分を点検する」としか書かれておらず、別コンテキストのレビュアーは毎回全体を見直して周辺の既存欠陥を拾う。
   提案：**ラウンド 2 以降は「前ラウンドの指摘の解消 ＋ 当該ラウンドの差分の must/should」に限定し、それ以外の発見は
   backlog へ回す**と明記する。今回はこれを手で行ってラウンド 7 で収束した。
2. **`aidev debug` の発火条件に「原因が特定済み」の逃げ道を作る**。
   `maxSendBacks` を超えると `verify` が WARN を出し続けるが、差し戻しの原因が毎回異なり、その場で特定・再現できている
   ケースでは委譲の価値が無い（今回は D111 に理由を書いて回避した）。提案：`aidev debug skip --reason "<…>"` を用意し、
   記録を残したうえで WARN を消す（「黙って無視」と「理由を書いて省く」を区別する）。
3. **「沈黙する失敗」への注意を protocol に入れる**。`pnpm -s` の再帰実行は失敗しても何も出力せず、終了コードだけが変わる。
   今回これで誤った結論を decisions.md に書いた（後で訂正）。提案：protocol.md「7.（主張と証拠）」に
   **「出力の有無で成否を判断しない。終了コードを別に確認する」**を 1 行足す。
4. **`metrics` の `sent_backs` の読み方を明記する**。`unapprove` が各工程に記録を残すため、per-phase の `sent_back` は
   「差し戻しの回数」より大きく出る（今回：親の表は 6、per-phase の合計は 8）。retro で誤読しやすい。
5. **タスク点検（`taskcheck`）の効果が大きいことを skill 側の推奨に反映する**。今回は点検 100 件 : review のラウンド指摘 78 件で、
   点検のほうが多く、かつ早い段で潰れている。`aidev-40-coding` の手順 5 は条件付き（autonomous は全タスク）だが、
   **`mode: interactive` でも「共有モジュール・外部に見える振る舞い」に触るタスクは既定で点検する**ことを推奨に格上げする提案。
