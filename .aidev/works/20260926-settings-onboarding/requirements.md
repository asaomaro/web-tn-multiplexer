# 要件: 設定の onboarding（初回の案内。H25b）

紐づく charter ゴール: `.aidev/charter.md` は本リポジトリに無いため対象外。

## 背景 / 課題

herdr には初回起動時の案内（onboarding）がある。herdr のソース（`/workspaces/web-tn-multiplexer/scratchpad/herdr/`）で確かめた事実:

- **いつ出すか**: 設定ファイルの `onboarding` が**無いか `true`** なら出す（`src/config.rs:94-96` の `should_show_onboarding` が
  `self.onboarding.unwrap_or(true)`）。既定の設定ファイルの説明は「Missing also shows onboarding; set false after you've chosen.」
  （`src/main.rs:68-70`）。クライアントの起動時にこの値を読み（`src/client/mod.rs:167`）、画面の状態を作るときに案内を開く
  （`src/client/shell/state.rs:964-967`）。
- **何を見せるか**（現行版）: 製品名と一言、「マウスで操作できる端末（サイドバーのクリック・枠のドラッグ・右クリックのメニュー）」、
  「`ctrl+b` で prefix、`?` でキー一覧と設定」、「次: エージェント連携を入れると状態が確かになる」（`src/ui/onboarding.rs:3-15`、
  描画は `src/client/shell/overlays.rs:534-620`）。ボタンは［↵ continue］だけ。
- **初期の版は通知の選択だった**: 0.2 系の CHANGELOG に「first-run onboarding flow that lets you choose notification preferences
  (sound and toast)」（`CHANGELOG.md:1190`）。のちに連携の案内に変わった（`CHANGELOG.md:722`）。
- **いつ二度と出さないか**: 続ける（Enter・→・`l`・ボタンのクリック）と、設定ファイルへ `onboarding = false` を書き込み
  （書けなくても先へ進み、診断を出す）、設定画面の「連携」の節を開く（`src/client/shell/overlay_input.rs:177-190`・`:477-485`、
  `src/client/shell/mouse.rs:667-673`、テスト `src/client/shell/tests/startup_overlays.rs:353-455`）。
- **モーダル**: 案内が開いている間、文字・貼り付け・外側のクリックは端末や popup へ届かない（`src/client/shell/input.rs:173-183`・
  `:205-215`、テスト `startup_overlays.rs:292-351`）。製品のお知らせより優先する（`state.rs:1492`、テスト `startup_overlays.rs:272-290`）。
- **スキップ・開き直し**: 画面上のスキップ・Esc は無い（続けるしか無い）。開き直す UI も無く、設定ファイルの `onboarding` を消すか
  `true` にすれば次の起動でまた出る。

Web 版（本製品）には初回の案内が無い。新しいブラウザで開いた利用者は、空の端末を前に、prefix・キー一覧（`prefix+?`）・設定
（`prefix+s`・サイドバーの［メニュー］→「設定」・モバイルの上のバーの「設定」）の存在を、pane に最初にフォーカスが入ったときの
4 秒のトースト（`packages/web/src/components/Toast.vue:14,35-45`）でしか知らない。テーマ（20260921-theme-settings）・キーの
プリセット（20260922-keybinding-presets）・通知（20260920-agent-notifications）は設定画面で選べるが、選べること自体に気づく入口が無い。
`docs/herdr-parity.md` の H25b 行は「onboarding は対象外のまま」と記録している。

## 目的 / ゴール

- 新しいブラウザで初めて本体の画面を開いた利用者が、最初の画面で**主要な操作の入口**（prefix・キー一覧・設定の開き方）を知り、
  **主要な選択**（テーマ・キーのプリセット・通知）をその場で済ませるか、既定のまま始めるかを選べる状態。
- すでにこのブラウザで使っている利用者の画面には、案内が突然出ず、保存された設定も変わらない状態。
- 案内を閉じたあとでも、利用者が自分でいつでも案内を開き直せる状態。

## ユーザーストーリー

- US1: 初めて使う利用者として、最初に開いたときに主要な操作の入口を知りたい。なぜなら空の端末からは prefix や設定の存在に
  気づけず、トーストは 4 秒で消えるから。（受け入れ: AC1, AC7）
- US2: 初めて使う利用者として、テーマ・キーのプリセット・通知を最初にまとめて選びたい。なぜなら設定画面を探し回らずに、
  自分の好みの状態から使い始めたいから。（受け入れ: AC3, AC9）
- US3: すぐ使い始めたい利用者として、案内を読まずに閉じたい。なぜなら既定のままで困らない人に、選択を強いたくないから。
  （受け入れ: AC4, AC5）
- US4: すでに使っている利用者として、アップデート後に案内が突然出たり、設定が変わったりしてほしくない。なぜなら作業の途中で
  モーダルに遮られ、選んだ設定が上書きされると困るから。（受け入れ: AC2, AC8, AC11）
- US5: 案内を閉じたあとで選び直したくなった利用者として、案内を開き直したい。なぜなら最初は飛ばしたが、あとで一式を見直したいから。
  （受け入れ: AC6）
- US6: キーボードだけで操作する利用者・モバイルの利用者として、案内を自分の手段だけで最後まで通したい。なぜなら案内がモーダルで、
  通せないと本体に進めないから。（受け入れ: AC-I1〜AC-I5, AC10）
- AC12（docs の更新）はストーリーに紐づかない（スコープの「対象」の最後の項目から来る）。

## スコープ

### 対象

- 初回の案内（ダイアログ）を、条件を満たすブラウザで本体の画面を開いたときに 1 回だけ開く。
- 案内の内容: 製品の一言・主要な操作の入口（prefix・キー一覧・設定を開くキー。現在の割り当てで表記）・テーマ・キーのプリセット・
  通知の選択。
- 確定（選んだ内容を反映して閉じる）と、スキップ（何も変えずに閉じる）。どちらでも「案内済み」を覚える。
- 設定画面から案内を開き直す導線。
- `docs/herdr-parity.md` の H25b 行と、利用者向けの確認手順（`docs/verification.md`）の更新。

### 対象外

- サイドバー行の色の条件付け・独自トークン（H21）——同じ backlog 行の残り。backlog に残す（decisions D1）。
- 「案内済み」をサーバやアカウントに持つこと。本製品の設定は**ブラウザごと**（`wtm.prefs.v1`。`packages/web/src/store/view.ts:47-73`）
  なので、案内済みもブラウザごとに持つ。
- 設定画面の項目のうち、テーマ・キーのプリセット・通知以外（表示・端末・色の上書き・個々のキーの割り当て・エージェント連携の導入）を
  案内の中で選ばせること。これらは設定画面で選べることを案内で伝えるだけにする。
- herdr の「続けると設定画面の連携の節を開く」の再現。本製品のエージェント連携はサーバ全体の設定（ブラウザごとではない）で、
  導入はサーバのファイルを書き換える操作なので、初回の案内から直接押させない。連携があること・設定画面にあることを案内で伝える。
- E2E（`packages/e2e`）の追加・実行（利用者の方針。検証はコンポーネントテストで行う）。

## 機能要件

- F1: 起動時に「案内を出すか」を 1 回だけ判定する。出すのは、このブラウザに本製品を使った痕跡が無いときだけ。
- F2: 案内は本体の画面（ログイン画面・切り離し画面ではない）の上にモーダルで開く。デスクトップとモバイルの両方で開く。
- F3: 案内の中で、テーマ・キーのプリセット（使わない／既存のプリセットのどれか）・通知（トースト・OS 通知・音）を選べる。
  初期値は現在の設定（初回なら既定。キーのプリセットは「使わない」）。
- F4: 確定すると、選んだ内容を**設定画面で選んだのと同じ保存値**として反映する。スキップ（［スキップ］・Esc）では何も反映しない。
- F5: 確定・スキップのどちらでも「案内済み」を保存し、以後の起動では開かない。
- F6: 設定画面から案内を開き直せる。開き直しても「案内を出すか」の判定や保存済みの設定は変えない（確定したときだけ反映する）。
- F7: 案内が開いている間、端末への入力・prefix の操作・背後の部品の操作が起きない。

## 非機能要件 / 制約

- 既存の保存値との互換: 案内を足しても、既存の `wtm.prefs.v1` の値の読み方・既定値は変えない。案内を開かない判定では何も書かない。
- 保存（`localStorage`）が読めない・書けない環境で壊れない。読めないときは案内を出さない（毎回出して邪魔しない側に倒す。
  先例: `Toast.vue:20-26` の `hasShownHint`）。
- 保存値の読み書きは `readPrefs`/`writePrefs` に集約する方針（`store/view.ts:49-73`）に従う。
- 文言は日本語。設定の説明と同じく「このブラウザにだけ残る」ことを伝える。
- 検証は vitest（コンポーネントテストで DOM・属性・`document.activeElement` を確かめる）。E2E は走らせない。

## 完了条件 (受け入れ基準)

- [ ] AC1: 「案内済み」の印が無く、かつ保存された設定（`wtm.prefs.v1`）・キー一覧の案内の表示済みの印（`wtm.hint.prefixHelp.v1`）・
  エージェントの既読の記録（`wtm.seen.v1`）のいずれも無いブラウザで本体の画面を開くと、案内が開く。
- [ ] AC2: 上の 3 つのうち 1 つでもあるブラウザ（既存の利用者）では、案内は開かず、保存値は 1 バイトも変わらない。
- [ ] AC3: 案内でテーマ・キーのプリセット・通知を選んで確定すると、設定画面で同じものを選んだときと同じ保存値になり、その場で効く。
  キーのプリセットを選ばない（「使わない」）ときはキーの割り当てを変えない。
- [ ] AC4: 案内をスキップ（［スキップ］・Esc）すると、テーマ・キー・通知の保存値は変わらない。
- [ ] AC5: 確定・スキップのどちらのあとも、再読み込みした画面で案内は開かない。
- [ ] AC6: 設定画面の操作で案内を開き直せる。開き直した案内の初期値は現在の設定で、スキップすれば何も変わらない。
- [ ] AC7: 案内には prefix・キー一覧・設定を開くキーが**現在の割り当て**で表示される。割り当てが無い操作は、キーを書かずに別の入口
  （サイドバーのメニュー等）を案内する。
- [ ] AC8: `localStorage` が読めない環境では案内を開かない（例外で画面が壊れない）。
- [ ] AC9: 通知で OS 通知を選んで確定したとき、OS の許可を求める。許可されなかったときは OS 通知を入れず、その理由が分かる。
  通知の選択を確定したあとは、あとから出る「OS の通知でも受け取れますか？」の案内（`NotificationController` の sticky トースト）を出さない。
  スキップしたときは、その案内の扱いを変えない（今までどおり、最初の知らせのあとに出る）。
- [ ] AC10: モバイル（1 列の画面）でも案内が開き、画面からはみ出さず、画面上のボタンだけで確定・スキップできる。
- [ ] AC11: 案内を足しても、既存の設定の保存値の読み方・既定値は変わらない（既存の `settings`・`notifications` のテストがそのまま通る）。
- [ ] AC12: `docs/herdr-parity.md` の H25b 行と `docs/verification.md` が、案内の出る条件・スキップ・開き直し方を利用者に分かる形で説明している。

## 相互作用の受け入れ基準（UI を伴う work のみ）

- [ ] AC-I1 開く / 閉じる: 初回は起動時に自動で開き、2 回目からは設定画面の操作で開く。［スキップ］・Esc・［この設定ではじめる］で閉じる。
  背景（ダイアログの外）のクリックでは閉じない（初回の案内を誤って消費しない。herdr も外側のクリックを無視する）。
- [ ] AC-I2 確定 / 取り消し: ［この設定ではじめる］が確定で、選んだ内容を反映して閉じる。［スキップ］・Esc は取り消しで、選びかけた内容を
  反映せずに閉じる（どちらも「案内済み」は保存する）。
- [ ] AC-I3 キーボードだけで完結するか: 開く → Tab で各選択へ移る → 選ぶ → 確定（または Esc でスキップ）を、マウス無しで通せる。
- [ ] AC-I4 フォーカスの行き先: 開いたら案内の中（最初の操作できる要素）へ移る。閉じたら、開く前にフォーカスしていた pane へ戻る
  （既存のダイアログと同じ。起動直後で pane がまだ無ければ、最初にフォーカスされる pane に任せる）。
- [ ] AC-I5 既存の操作を妨げないか: 開いている間のキー（prefix を含む）・文字・貼り付けは端末へ届かず、prefix の操作も起きない。
  ダイアログの外のクリックは背後の部品（サイドバー・pane 等）へ届かない。
  閉じたあとは、端末への入力・prefix の操作が今までどおり効く。

- 「案内済み」の保存先（`wtm.prefs.v1` の 1 項目か、別のキーか）。design で決める。既存の利用者の判定に使う痕跡は AC1・AC2 の
  3 つで確定とし、research では「初回の利用で書かれるか」を事実として確かめるだけにする。
- モバイルでキーのプリセットを出すか（画面のキーボードでは組み合わせのキーを使えない）。design で決める。
- 起動直後、pane へのフォーカス（`client.hello` の後）と案内のフォーカスの取り合い。research で確かめる。
