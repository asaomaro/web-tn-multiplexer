# 決定記録

## D1: AC13 は coding ではなく test 工程で消化する

- 背景: AC13 は「既存の単体テストと既定の E2E が通る」ことを求めるもので、design でも
  「既存テスト・E2E の通過」で確認するとしている。対応する T14 は一式を走らせるだけで、
  coding 工程で書く差分を持たない。
- 決定: **T14 は coding 工程では未チェックのまま承認してよい**（`aidev-30-tasks` 手順 6）。消化は test 工程。
- 理由 / 代替案: coding 中に毎回 E2E 一式（約 4 分）を回すと刻みが粗くなる。各タスクの直後に回すのは
  触ったパッケージの単体テストまでとする。
- 影響: `aidev-40-coding` の「完了の目安」と形の上で食い違うので、この記録を証跡とする。

## D2: タブの ＋ が Tab の到達順を変えるので、既存 E2E 2 件を直す

- 背景: ＋ は Tab で止まる `<button>` なので、タブバーから Tab で進む順に 1 つ挟まる。
  `keys-mouse-dialogs.spec.ts:230-233`（タブから Tab 1 回で枠へ）と `:293-299`
  （順が `["splitter","frame@pane2"]`）が必ず落ちる。design の独立点検が実地に指摘した。
- 決定: **＋ を Tab の対象から外さず、既存 E2E の期待を直す**。
- 理由 / 代替案: 代替は `tabindex="-1"` で Tab から外すことだが、**AC-I3 が「足した 5 つのボタンが
  Tab で到達できる」ことを求めている**。マウス専用のボタンを足すのは、キーボードだけで使う人を締め出す。
  順が変わるのは「操作を 1 つ足した」結果として正しい変化で、隠すべきものではない。
- 影響: AC13 の但し書き（テストを直した理由が AC に紐づくこと）に当たる。紐づく先は AC6・AC-I3。
  **直す前に一度落として、変わったことを確かめる**（T9）。

## D3: サイドバーのフッタは下端に固定せず、内容と一緒にスクロールさせる

- 背景: herdr はサイドバーの最下段にボタンの帯を固定している。同じにするには `.sidebar` の
  `overflow-y: auto` を内側の入れ物へ移す必要がある。
- 決定: **移さない**。`margin-top: auto` で「内容が短いときは下端に寄る」だけにする。
- 理由 / 代替案: `.sidebar` がスクロール主体であることは、**先行 work（`20260920-ui-selection-visuals`）の
  AC3 の E2E が `.sidebar` の `scrollWidth <= clientWidth` で判定している前提そのもの**。
  内側に入れ物を作ると `.sidebar` は溢れなくなり、**あの判定が何も確かめない状態になる**
  （テストは緑のまま、守っているはずの性質だけが消える）。
- 影響: 行が多いときフッタが画面外へスクロールする。backlog へ送り、**判定の作り直しと同時に**やる。

## D4: AC14 の最初のテストは「何も確かめていなかった」ので書き直した

- 背景: AC14（足したボタンが端末の大きさを変えていない）を、当初
  **「`.tab-bar` の高さ === `.tab-bar-item` の高さ ＋ 下線」**で確かめようとした。実装後に通ったので
  そのまま採用しかけたが、条項 `regression-negative-control` に従って壊して確かめたところ、
  **`.tab-bar-new` の `padding` を `0.5em` → `0.9em` にしても通った**。
- 原因: `.tab-bar` は flex の行で、`align-items` が既定（stretch）。**タブも ＋ も同じ行の高さへ
  引き伸ばされる**ので、＋ が行を押し広げるとタブの高さも一緒に増える。
  等式は ＋ が何 px でも成り立ち、**この判定は構造上落ちようがなかった**（実測: padding 0.9em で
  タブ・＋ とも 44.78px、帯 45.78px。等式は成立）。
- 決定: **「＋ を `display:none` にしたときの帯の高さと、表示したときの帯の高さを比べる」**に書き直した。
- 理由 / 代替案: これなら「＋ があることで帯が高くなったか」を直接測る。
  代替の「`cols` / `rows` の固定値」は、xterm のフォントを指定していないので環境依存で再現しない。
- 影響: 書き直したテストは、壊した状態（padding 0.9em）で**あり 45.78 / なし 33** と報告して落ちる。
  元に戻すと通る。**負の対照が無ければ、緑のまま何も守らないテストを着地させていた**。

## D5: タスク点検を 1 委譲 1 タスクではなく、5 本にまとめた（規約からの逸脱）

- 背景: `protocol-check.md`「(b)」は **「1 委譲 = 1 タスク」**を求める。理由は、まとめると
  `task_checks` が実際のコンテキスト数より多くなり、「1 コンテキストが何件拾ったか」を後から復元できなくなるため。
- 決定: この work（16 タスク）では **5 本の委譲にまとめた**（T1-T3 / T4-T5 / T6-T7 / T8-T9 / T10-T13 / T14-T16）。
  各委譲には**タスクごとに見出しを分けて結論を出す**よう指示し、指摘はタスクに紐づけて記録する。
- 理由 / 代替案: 16 本を個別に回すと待ち時間が支配的になる。まとめた代わりに、
  **失われるのは「1 コンテキストあたりの検出数」だけ**で、「どのタスクに何件の指摘が出たか」は
  見出しで保たれる。効果測定の粒度が粗くなることを承知のうえでの交換。
- 影響: `aidev taskcheck report` には**タスクごとの件数**を刻むので `task_check_findings` は実態と合うが、
  `task_checks`（16）は**委譲したコンテキストの数（5）とは一致しない**。
  横断の効果測定でこの work を使うときは、この記録を見ること。

## D6: 並び順のボタンは、内部の値ではなく日本語の表示名を出す

- 背景: herdr は**順序名そのものをボタンにする**流儀で、`grouped` / `priority` と出す。
  それをそのまま写したところ、**この製品の UI でここだけ英語の内部値が露出した**
  （他は「＋ 新規」「メニュー」「キー割り当て」「移動」「切り離し」と全て日本語）。
  `aria-label` も「並び順: grouped」となり、読み上げでも生値が出る。review のラウンド 1 で指摘。
- 決定: **「グループ順」「優先度順」**を表示する。内部の値（`grouped` / `priority`）は
  `localStorage` とストアの中だけに留める。
- 理由 / 代替案: 利用者の依頼文は「ソート順を priority、grouped で設定できるボタン」と
  **herdr の値の名前で**書かれていたので、英語のまま出す選択もあった。それでも日本語にしたのは、
  (1) herdr は英語 UI なので「順序名そのもの」が自然だが、この製品は日本語 UI で、
  ここだけ内部値が出ると**何の順かが読めない**。(2) 「グループ順」は herdr の `grouped`
  （workspace ごとにまとまる）と 1 対 1 で対応し、概念の対応は失われない。
- 影響: 表示を英語に戻したいときは `Sidebar.vue` の `AGENT_SORT_LABEL` の 1 行を変えるだけでよい。
  **この判断は利用者の依頼文の字面から外れているので、PR とユーザーへの報告で明示する。**
