# 要件: サイドバーの workspace 行のメニューをキーボードから開く

## 背景 / 課題

サイドバーの workspace 行（`Sidebar.vue`）は、右クリック（`@contextmenu`）でしかコンテキストメニュー
（「開く」「名前を変更」「worktree を開く…」等）を開けない。`tabindex`・`keydown` が一切無く、
マウス以外での到達手段が無い。

一方、pane の枠（`PaneFrame.vue`）は既にキーボードから同じコンテキストメニューを開ける
（roving tabindex・Enter/Space/ArrowDown/Shift+F10/ContextMenu キー・`getBoundingClientRect()`
からの位置計算）。herdr はキーボードだけで完結する操作性を持つツールであり、この非対称は
herdr パリティのギャップである。

このリポジトリには既に「navigate モード」（`prefix+w` で開始し、矢印キーで workspace 行の選択
カーソルを動かし、`Enter` で選択した workspace へフォーカスを移す・`Escape` でキャンセルする
既存の機能。`Sidebar.vue` は現在の選択行を `sidebar-row-selected` クラスで可視化する）がある。
navigate モードは既に「サイドバーの workspace 行を1つ選ぶ」までは実現しているが、選んだ行の
メニューを開く手段が無い（`Enter` は「フォーカスして navigate モードを抜ける」に固定済みで、
メニューを開く動作ではない）。

具体的にこのギャップが表面化した例: 20260920-git-worktree-actions の decisions.md で
「『worktree を開く…』がキーだけで到達できない」と記録されている（**その work の AC-I3**——
本書が後段で定義する AC-I3 とは別 work の別の基準なので混同しないこと）。これは worktree
メニュー項目固有の問題ではなく、workspace 行のメニュー全体がキーボードから開けないという、
より根本的なギャップの一例である。

## 目的 / ゴール

サイドバーの workspace 行のコンテキストメニューが、マウスを使わずキーボードだけで開き・操作し・
閉じられる状態にする（実現方法は「スコープ / 対象」参照——既存の navigate モードを拡張し、
新しい別の選択の仕組みは作らない）。

## ユーザーストーリー

- US1: マウスを使わずキーボードだけで操作したい利用者として、サイドバーの workspace 行の
  コンテキストメニュー（開く・名前を変更・worktree を開く等）をキーボードだけで開いて使いたい。
  なぜなら、pane の枠は既にキーボードから同じ操作ができるのに、workspace 行だけできないのは
  一貫性が無く、herdr が持つ「マウス無しで完結する」体験を損なうから。（受け入れ: AC1, AC2, AC3,
  AC-I1, AC-I2, AC-I3, AC-I4, AC-I5）

## スコープ

### 対象

- navigate モード（`prefix+w` で開始、矢印キーで workspace 行を選択する既存の機能）に、
  選択中の workspace 行のコンテキストメニューを開く新しいキー操作を追加する。
- メニューの位置計算は、選択中の行の DOM 要素の `getBoundingClientRect()` から行う
  （`PaneFrame.vue` の既存のキーボード起動時の位置計算と同じ考え方。マウス座標に依存しない）。
- 開いたメニューの内容・その後の操作（メニュー内でのキー操作・項目の確定・Escape での閉じ方）は
  既存の `ContextMenu.vue`（`PaneFrame.vue`・`Sidebar.vue` 双方が既に使っている共有コンポーネント）
  をそのまま使う。メニュー自体の新しい変更は行わない。

### 対象外

- **サイドバー行への独立した Tab フォーカス（`PaneFrame.vue` の roving tabindex 方式を
  workspace 行へそのまま複製すること）**: navigate モードが既に「workspace 行を1つ選ぶ」という
  同じ役割を担っており、重複する2つ目の選択の仕組みを作らない（herdr パリティ調査で確認した
  既存の設計判断——`GotoPicker.vue` も同じ「1つの ref + ハイライト」方式で、この方式がこの
  アプリの確立した list 選択の慣習）。
- **グループ見出し行（手動グループ・自動グループの見出し）のメニューをキーボードから開くこと**:
  `Sidebar.vue` の `onRowContextMenu` は行の種類（workspace / group）で分岐しているが、この
  work は workspace 行のメニューに絞る。グループ見出し行への対応は別途検討する。
- **agent 行（サイドバーのエージェント一覧）のメニューをキーボードから開くこと**: 現状
  `@click` のみでコンテキストメニュー自体を持たない別の行の種類であり、この work の対象外。
- **既存の Enter（navigate モードの「確定＝フォーカス」）・Escape（キャンセル）・矢印キーによる
  行の移動の挙動を変えること**: 全て現状のまま。新しいキー操作は、これらと衝突しないキーを
  design で選ぶ。

## 機能要件

- navigate モードで workspace 行が選択されている間、新しいキー操作（design で確定）を押すと、
  その行の既存のコンテキストメニュー（マウスの右クリックと全く同じ内容・全く同じ
  `ContextMenu.vue`）が開く。
- メニューが開いている間・閉じた後の navigate モードの状態（選択が保持されるか、モードを抜けるか
  等）は design で確定する。既存の Enter・Escape・矢印キーの挙動は変えない。

## 非機能要件 / 制約

- 新しいキーは、navigate モードが既に予約しているキー（矢印キー・Enter・Escape）と衝突しない
  こと。
- navigate モードの外（通常の端末入力・他の既存キーバインド）には、新しいキー操作の影響が
  一切及ばないこと（AC-I5 の根拠）。
- 既存の `PaneFrame.vue` のキーボード起動パターン（`getBoundingClientRect()` からの位置計算・
  `actions.openContextMenu(...)` の呼び出し）と一貫した実装にする。

## 完了条件 (受け入れ基準)

- [ ] AC1: navigate モードで workspace 行を選択した状態で新しいキー操作を押すと、その行の
  コンテキストメニューが開く。
- [ ] AC2: 開いたメニューの内容は、同じ行を右クリックしたときと同じ（項目・並び・挙動とも）。
- [ ] AC3: 既存の Enter（フォーカスして navigate モードを抜ける）・Escape（キャンセル）・
  矢印キーによる行の移動は、この work の変更後も従来どおり動作する（非破壊）。

## 相互作用の受け入れ基準（UI を伴う work のみ）

- [ ] AC-I1 開く / 閉じる: navigate モードで行を選択した状態から新しいキー操作でメニューが開く。
  メニューは Escape で閉じる（既存の `ContextMenu.vue` の挙動）。
- [ ] AC-I2 確定 / 取り消し: メニュー項目を選んで確定すればその操作が実行される。Escape で
  取り消せば何も実行されない。
- [ ] AC-I3 キーボードだけで完結するか: `prefix+w`（navigate モード開始）→ 矢印キーで
  workspace 行を選択 → 新しいキー操作でメニューを開く → メニュー内の操作 → 確定/取消、の
  一連をマウス無しで通せる。
- [ ] AC-I4 フォーカスの行き先: メニューを閉じた後、どこにフォーカス・選択状態が戻るかを
  design で確定し、利用者が迷わない場所（navigate モードの選択状態、または端末）に戻る。
- [ ] AC-I5 既存の操作を妨げないか: 新しいキー操作は navigate モードの外側（通常の端末入力・
  他のキーバインド）に影響しない。既存の Enter・Escape・矢印キーの意味を変えない。

## 未確定事項 / 確認したいこと

- メニューを開く具体的なキー（`Space`・`Shift+F10`・`ContextMenu` キーのいずれか、または複数）は
  design で確定する。navigate モード内で未使用のキーであることを design 時に再確認する。
- メニューを閉じた後、navigate モードの選択状態を保持するか、モードごと抜けるかは design で
  確定する。
- この新しいキー操作を、Enter・Escape と同じく「固定（カスタマイズ対象外）」にするか、既存の
  移動キー（`keys/navigateKeys.ts`）と同じくカスタマイズ可能にするかは design で確定する
  （herdr-parity.md H26c が Enter/Escape を固定・カスタマイズ対象外としている前例がある）。
