# 要件: Claude Code・Codex 以外の6エージェントへセッション再開対応を広げる

紐づく charter ゴール: なし（`.aidev/charter.md` 未導入。herdr 対応表 H32・
backlog「セッション永続化の拡張」に基づく）

## 背景 / 課題

`20260923-agent-session-resume` で、Claude Code・Codex に限定してサーバ再起動後の会話再開を実装した
（各エージェントの公式 `SessionStart` フックが会話IDを報告し、`AgentIntegrationInstaller` が導入・解除・
状態確認を担う）。その work の requirements は「Claude Code・Codex 以外は、各エージェント自身の
公式フック機構の仕様が本 work のリサーチ範囲では未確認」を理由に対象外とし、
`.aidev/backlog/product-roadmap.md` へ後続として残した（herdr が resume 対応と記載する残り16種）。

本 work はその後続の一部に着手する。ただし16種そのままではなく、以下の3段階の絞り込みを経た
**6エージェント**を対象にする（利用者との協議・実地調査で確定。decisions.md D1〜D3）：

1. herdr が「session identity」型（hook はセッションIDの報告だけを行い、状態判定は引き続き画面検出——
   本製品の既存の Claude Code・Codex と同じ統合方式）と分類する10エージェントに絞った
   （「lifecycle authority」型6エージェントは状態そのものを hook が報告する別方式で、本製品が
   未実装のアーキテクチャを新設することになるため、別の backlog 項目へ切り出した）。
2. その10エージェントのうち、公式ドキュメントを実地に確認したところ Antigravity CLI・Qoder CLI の
   2つは実際には `SessionStart` 相当の hook（セッション開始時に一度だけ発火し、セッションIDを
   取得できるイベント）を持たないと判明し、対象から外した（research.md F1）。
3. 残った8エージェントについて、design 直前に exact な設定ファイル構造・stdin JSON のフィールド名を
   一次資料で個別に再確認したところ、Letta Code・Hermes Agent の2つは**セッションIDの受け渡し方法が
   ドキュメント上で確認できず**（Hermes Agent はさらに、本製品が前提とする「shell コマンドを
   サブプロセスとして起動する」方式と噛み合わない可能性が高いことも判明）、対象から外した
   （decisions.md D3）。

**対象6エージェント**: Cursor Agent CLI・GitHub Copilot CLI・Devin CLI・Droid（Factory AI）・
Grok CLI（xAI Grok Build）・Qwen Code。いずれも設定ファイルの構造・hook エントリの形・セッションIDの
受け渡しフィールド名まで公式ドキュメントで確認済み（decisions.md D3）。

## 目的 / ゴール

上記6エージェントについても、Claude Code・Codex と同じ体験（連携を明示的に導入した pane に限り、
サーバ再起動後に直前の会話が自動的に再開される。未導入・未検出の pane は現状どおり普通のシェルで
復元される）が得られる状態にする。

**この work 固有の制約として明記する**: 対象6エージェントは、いずれも本開発環境に実機が存在せず
インストール・動作確認ができない（research.md「実現性 / リスク」参照）。したがって本 work の
「完了」は、**公式ドキュメントの記述どおりに実装され、単体テストで書き込み内容の形が正しいことを
検証した状態**を指し、「実機で実際に resume が動く」ことの確認は含まない
（`20260923-agent-session-resume` decisions D5 の Windows named pipe と同じ扱いを、6エージェント
全体に広げたもの。この制約を利用者へ可視化する記録先は AC8 で定める）。

## ユーザーストーリー

- US1: Cursor・GitHub Copilot・Devin 等、Claude Code・Codex 以外のエージェントを使う利用者として、
  サーバの再起動を挟んでも会話の続きから作業したい。なぜなら、Claude Code・Codex ユーザーだけが
  この体験を得られる状態は不公平で、複数エージェントを併用する利用者はエージェントによって
  挙動が変わることに戸惑うから。（受け入れ: AC1〜AC6）
- US2: 複数の pane で同時に同じエージェントを動かす利用者として、それぞれの pane が
  それぞれ別々の会話として正しく再開されてほしい（`20260923-agent-session-resume` の US2 と同じ理由を
  6エージェントすべてに適用する）。（受け入れ: AC5）
- US3: この機能を望まない利用者として、自分のエージェントのグローバル設定が無断で書き換わってほしくない
  （同 US3 と同じ）。（受け入れ: AC2, AC3, AC-I1〜AC-I2）

## スコープ

### 対象

- 6エージェント（Cursor Agent CLI・GitHub Copilot CLI・Devin CLI・Droid・Grok CLI・Qwen Code）それぞれの
  公式フック機構を使って、会話（セッション）IDを pane ごとに捕捉する仕組み。
- 捕捉した ID を `session.json` に永続化し、サーバ再起動時の pane 復元で各エージェントの resume
  コマンド（research.md F2 参照。例: `cursor-agent --resume <id>`）を自動投入して再開する。
- 連携の導入（有効化）・解除・状態確認は、既存の設定画面（Claude Code・Codex の節）と同じ体験を
  6エージェント分に広げる。
- 複数 pane が同一ディレクトリ・同一エージェント種別でも、pane ごとに正しく別々の会話として
  再開されること（`20260923-agent-session-resume` requirements の AC5 と同じ要件。本書では
  下記「完了条件」の AC5 として再定義する）。
- ID が失効・存在しない・エージェントが未検出などの場合は、現状どおり普通のシェルで復元する
  フォールバックを崩さないこと。
- 6エージェントとも設定ファイルの構造・hook エントリの形が既存の Claude Code・Codex とそれぞれ異なる
  （decisions.md D3。「6エージェント全て、既存コードの流用ではなく個別のエントリ構築・解析ロジックが
  要る」——design で構造を確定する）。

### 対象外

- herdr が「lifecycle authority」型と分類する6エージェント（Kimi Code CLI・OpenCode・Kilo Code CLI・
  MastraCode・Pi・OMP）。状態そのものを hook が報告する別方式で、本製品が未実装のアーキテクチャが
  要るため、別の backlog 項目のまま残す。
- Antigravity CLI・Qoder CLI（`SessionStart` 相当の hook が存在しないと判明したため。
  research.md F1・`.aidev/backlog/product-roadmap.md`「非対応」行）。
- Letta Code・Hermes Agent（セッションIDの受け渡し方法がドキュメント上確認できなかったため。
  decisions.md D3・`.aidev/backlog/product-roadmap.md`「非対応」行）。
- 実機での動作確認・E2E（対象6エージェントとも本環境にCLI実体が無いため。上記「目的 / ゴール」参照）。
- 画面履歴（scrollback）の保存・再生・名前付き session・サーバ更新時の live handoff
  （`20260923-agent-session-resume` requirements の対象外と同じ理由。それぞれ別の backlog 項目）。

## 機能要件

- 各エージェントの公式フック（`SessionStart` 相当。research.md F2・decisions D3 の一覧）を使い、
  エージェントが起動・再開するたびに「そのプロセスがどの pane に属するか」と「会話/セッションの
  識別子」を本製品のサーバへ報告できること。既存の報告受信の**経路**（本製品サーバ側の受け口）は
  6エージェント共通で再利用するが、6エージェントとも hook 設定ファイルの構造・stdin JSON の
  フィールド名がそれぞれ異なる（decisions D3）ため、**エージェントごとの hook エントリ構築・
  設定ファイル解析ロジックは個別に実装する**（既存の Claude Code・Codex 向けコードの単純な
  横展開では済まない）。
- 報告された識別子は pane ごとに保持し、`session.json` に永続化すること（既存の仕組みをそのまま使う）。
- 連携（フック）の導入・解除は、設定画面から明示的な操作で行えること（既存の Claude Code・Codex の節と
  同じ UI パターンを6エージェント分に広げる。テンプレートの複製をしない——研究で確認した
  `AGENT_INTEGRATION_KINDS` 配列駆動の構造を使う。この構造上の再利用により、既存の Claude Code・Codex の
  節を含め、設定画面の他の項目のテンプレート・操作性は変更されない——AC-I4 の裏付け）。
- 導入済みかどうかを設定画面で確認できること（既存と同じ）。
- 復元時、保存された識別子が有効に見えなければ、現状どおり普通のシェルで復元すること。

## 非機能要件 / 制約

- **書き込み範囲の限定**（既存と同じ）: 利用者が明示的に導入操作をしたときに限る。
- **既存動作の非破壊**: Claude Code・Codex・連携未導入の pane の復元動作に変化がないこと。
- **クロスプラットフォーム**: 既存と同じ前提（Linux・Windows）。ただし実機確認ができないため、
  各エージェントの設定ファイルパスが Windows でどう変わるか（環境変数の既定値等）は、公式
  ドキュメントの記述をそのまま実装し、`docs/verification.md` に「未検証」として明記する。
- **一次資料の再検証を徹底する**: このリサーチの過程で、生成された調査報告に誤り（存在しない hook を
  「存在する」と報告した例。research.md F1）が実際に混入していたことが分かった。design・coding の
  各段階で、各エージェントの設定ファイルの exact なフィールド名・パスを実装直前にもう一度
  一次資料（公式ドキュメントのURL）で確認してから書くこと（推測・パラフレーズだけで実装しない）。
- **herdr との差異の記録**（既存と同じ）: herdr 独自のプロトコルには依存せず、各エージェントの
  公式フック機構を直接使う。

## 相互作用の受け入れ基準（UI を伴う work）

- [ ] AC-I1 導入操作: 設定画面から、対象6エージェントそれぞれの連携を個別に有効化できる。有効化前に
  「何が変わるか」が分かる説明を提示し、明示的な操作でのみ実行される（既存の Claude Code・Codex と
  同じ体験）。
- [ ] AC-I2 解除操作: 有効化した連携を、設定画面から無効化できる。
- [ ] AC-I3 状態表示: 現在の導入状況が設定画面から確認できる。
- [ ] AC-I4 既存の操作を妨げない: 本機能の追加が、設定画面の他の項目（Claude Code・Codex の節を含む）の
  操作性に影響しないこと。

## 完了条件 (受け入れ基準)

- [ ] AC1: 対象6エージェントそれぞれについて、連携を有効化する設定画面の操作ができ、有効化すると
  そのエージェントの公式ドキュメントどおりの設定ファイル・hook エントリが書き込まれる

  無変更で通る（回帰なし）。
