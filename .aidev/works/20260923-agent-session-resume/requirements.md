# 要件: サーバ再起動後のエージェント会話の再開

紐づく charter ゴール: なし（`.aidev/charter.md` 未導入。herdr 対応表 H32・backlog「セッション永続化の拡張」に基づく）

## 背景 / 課題

本製品は herdr 同様、サーバ再起動後に workspace / tab / pane / cwd / レイアウト / フォーカスを復元する
（20260918-web-terminal-multiplexer D7・AC18・MVP）。しかし復元されるのは**空のシェル**だけで、
その pane で Claude Code や Codex が動いていても、再起動後は会話が失われ、利用者は手動で
`cd` し直し・エージェントを起動し直す必要がある（`packages/server/src/persist/SessionFile.ts` の
コメント「プロセスの実体は持たない（cwd から新しいシェルを起動して復元する）」のとおり、現状は意図的にそうなっている）。

herdr は「エージェント連携（H18・research.md F6.2）」経由で報告された**正確な会話ID**を使い、
`claude --resume <id>` / `codex resume <id>` のように再開する。この連携は herdr 独自のローカル socket
プロトコルで、対象エージェントごとに公式インテグレーション（フック）を利用者が明示的にインストールする
ことで有効になる（herdr 公式ドキュメント `session-state.mdx`/`integrations.mdx`/`agents.mdx` 実物で確認済み。
本 work の research.md に詳細）。

本 work では、この herdr の「連携フック→正確なIDで再開」の仕組みを、**Claude Code と Codex** を対象に、
本製品自身の統合として実装する（herdr の連携先には依存しない。Claude Code・Codex それぞれが持つ
**公式のフック機構**（Claude Code の `SessionStart` hook、Codex の `[features] hooks` 設定）を土台にする）。

**この2エージェントに限定する理由**（利用者との協議で確定）：
- 「IDなしで直近の会話を再開する」各CLI公式フラグ（`claude --continue` 等）だけで済ませる案も検討したが、
  **同一ディレクトリに同種エージェントの pane が複数ある場合、区別なく「直近の1つ」しか再開できない**
  （Claude Code は複数 pane が同じ会話ログに書き込み内容が混線する、Codex は2つ目以降がロックされる。
  research.md 参照）。利用者はこれを許容できないと判断し、pane ごとに一意な正確なIDでの再開を選んだ。
- Claude Code・Codex 以外のエージェント（herdr が resume 対応と記載する Pi・OMP・Kimi Code CLI・
  GitHub Copilot CLI 等 16 種）は、各エージェント自身の公式フック機構の仕様が本 work のリサーチ範囲では
  未確認（herdr 側の抽象化された記述しか無い）。**確実な情報が無いまま利用者のグローバル設定を書き換える
  実装はしない**——`.aidev/backlog/product-roadmap.md` に、判明した再開コマンド一覧（research.md）とともに
  後続として残す。

## 目的 / ゴール

サーバ（プロセス）が再起動しても、Claude Code・Codex を実行していた pane では、
**利用者が明示的に許可した場合に限り**、直前の会話が自動的に再開されている状態。
連携が導入されていない・IDが読み取れない pane は、現状どおり普通のシェルで復元される状態が保たれる
（herdr の「対応外・不明・失効した参照は普通のシェルとして復元する」と同じ割り切り）。

## ユーザーストーリー

- US1: Claude Code / Codex を常用する利用者として、サーバの再起動（更新・再起動ボタン・クラッシュ復帰等）を
  挟んでも会話の続きから作業したい。なぜなら、都度エージェントへ経緯を再説明する手間と、
  再起動そのものを避けたくなる心理的コストを無くしたいから。（受け入れ: AC1〜AC6）
- US2: 複数の pane で同時に Claude Code / Codex を動かす利用者として、それぞれの pane が
  **それぞれ別々の会話**として正しく再開されてほしい（同一フォルダで複数走らせていても、である）。
  なぜなら、直近1件だけしか戻らないのでは実質使い物にならず、会話の混線や上書きはなおさら困るから。
  （受け入れ: AC5, AC-I5）
- US3: 本製品を初めて使う・この機能を望まない利用者として、自分の Claude Code / Codex の
  グローバル設定が無断で書き換わってほしくない。なぜなら、他のツール（herdr 自身や CLI を直接使う場面）
  にも影響する設定だから、変更する・しないは自分で選びたい。（受け入れ: AC2, AC3, AC-I1〜AC-I2）

## スコープ

### 対象

- Claude Code・Codex を対象に、公式フック機構を使って「会話（セッション）ID」を pane ごとに捕捉する仕組み。
- 捕捉した ID を `session.json`（永続化）に保存し、サーバ再起動時の pane 復元で
  `claude --resume <id>` / `codex resume <id>` 相当のコマンドを自動投入して再開する。
- 連携の導入（有効化）は利用者の明示的な操作を要する UI（設定画面）。導入状況の確認・無効化も含む。
- 再起動後の自動再開そのものの ON/OFF 切替（連携を導入した後の既定動作）。
- 複数 pane が同一ディレクトリ・同一エージェント種別でも、pane ごとに正しく別々の会話として再開されること。
- ID が失効・存在しない・エージェントが未検出などの場合は、現状どおり普通のシェルで復元する
  フォールバックを崩さないこと。

### 対象外

- Claude Code・Codex 以外のエージェント（Pi・Gemini CLI・Cursor Agent CLI・GitHub Copilot CLI 等）への対応。
  `.aidev/backlog/product-roadmap.md` へ、research.md で判明した各エージェントの再開コマンド一覧とともに
  後続として残す。
- 画面履歴（scrollback）の保存・再生（herdr の `experimental.pane_history` 相当、H32 の別要素）。
- 名前付き session（H33）。
- サーバ**更新**時の live handoff（プロセスを引き継いだまま入れ替える。H32 の別要素。今回はサーバの
  「停止して起動し直す」再起動のみを対象とする——既存の D7 のレイアウト復元と同じ前提）。
- 「切り離して再接続」（`prefix+q`・herdr H30）のケース：このケースはプロセスが継続しており
  会話が失われないため、そもそも本機能の対象ではない（現状のまま）。

## 機能要件

- Claude Code の `SessionStart` フック、Codex の hooks 機能を使い、エージェントが起動・再開するたびに
  「そのプロセスがどの pane に属するか」と「会話/セッションの識別子」を本製品のサーバへ報告できること。
- 報告を受け取る経路は、他プロセス・他利用者から偽装されにくい形にすること（ローカル限定・pane 単位で
  正しく紐付くこと。非機能要件参照）。
- 報告された識別子は pane ごとに保持し、`session.json` に永続化すること（サーバプロセス自体の再起動を
  またいで必要なため）。
- 連携（フック）の導入・解除は、設定画面から明示的な操作で行えること。導入すると何が変わるか
  （どの設定ファイルに何を書き込むか）を利用者に分かる形で示すこと。
- 導入済みかどうか（Claude Code・Codex それぞれ）を設定画面で確認できること。
- 再起動時の自動再開の可否を、連携導入後に利用者が ON/OFF 切替できること（既定値は design で検討）。
- 復元時、保存された識別子が有効に見えなければ（無い・形式不正など）、現状どおり普通のシェルで復元すること
  （エラーで pane を `failed` にしない。herdr と同じ割り切り）。
- 復元コマンドの実行結果（成功したかどうか）を厳密には検査しない（herdr も検査していない。
  再開コマンドが失敗すればその出力がそのままシェルに残り、利用者はそこから通常操作を続けられる）。

## 非機能要件 / 制約

- **書き込み範囲の限定**: グローバル設定への書き込みは、利用者が明示的に導入操作をしたときに限る
  （自動検出しても黙って書き換えない）。
- **報告経路の安全性**: ローカルの別プロセス・別利用者が、任意の pane に対して偽の会話IDを報告できたり、
  他 pane の情報を読み取れたりしないこと（同一ホスト・同一起動インスタンスに閉じる。設計で具体化）。
- **既存動作の非破壊**: 連携を導入していない・対象エージェントでない pane の復元動作（現状のプレーンな
  シェル復元。D7・AC18）に変化がないこと。
- **クロスプラットフォーム**: Linux・Windows の両方で動作すること（MVP の対応 OS。AC16 と同じ前提）。
  Windows でのソケット/パイプ相当の実現方法は design で検討する。
- **herdr との差異の記録**: herdr 本来の「連携経由の正確なID再開」は herdr 独自のフォーマット・
  socket プロトコルに依存するため、本製品はそれを模倣せず、Claude Code・Codex それぞれの**公式**フック
  機構を直接使う（herdr 固有プロトコルへの依存を持たない）。この判断の理由を decisions.md に残す。

## 相互作用の受け入れ基準（UI を伴う work）

- [ ] AC-I1 導入操作: 設定画面から、Claude Code / Codex それぞれの連携を個別に有効化できる。有効化前に
  「何が変わるか（設定ファイルへの書き込み）」が分かる説明を提示し、明示的な操作でのみ実行される。
- [ ] AC-I2 解除操作: 有効化した連携を、設定画面から無効化（書き込んだ内容を取り除く）できる。
- [ ] AC-I3 状態表示: 現在の導入状況（有効/無効、対象エージェントの CLI が見つからない等）が
  設定画面から確認できる。
- [ ] AC-I4 自動再開の ON/OFF: 連携導入後、サーバ再起動時に自動で会話を再開するかどうかを
  切替えられる。切替は即座に反映される（次回の再起動から有効）。
- [ ] AC-I5 既存の操作を妨げない: 本機能の導入・設定操作が、既存の設定画面の他の項目
  （通知・テーマ・表示・端末・キー）の操作性に影響しないこと。

## 完了条件 (受け入れ基準)

- [ ] AC1: Claude Code の連携を有効化した状態で、ある pane で Claude Code の会話を進行中にサーバを
  再起動すると、その pane は同じ会話（Claude Code 自身の `--resume <id>` で見て同一の会話履歴）を
  再開した状態で復元される。
- [ ] AC2: Codex についても AC1 と同様に、`codex resume <id>` 相当で同一の会話が再開されること。
- [ ] AC3: 連携を有効化していない場合、Claude Code / Codex が動いていた pane も、現状どおり
  （AC18・D7）ただのシェルとして復元される（本機能導入前の挙動が壊れていない）。
- [ ] AC4: 連携を有効化していても、対象エージェントが検出されていない・識別子が報告されなかった
  pane は、現状どおりただのシェルとして復元される。
- [ ] AC5: 同一の cwd に、同一種別のエージェント（例: どちらも Claude Code）を実行している pane が
  2つ以上ある状態でサーバを再起動すると、**それぞれの pane がそれぞれ自分の会話を**再開する
  （どちらも同じ1つの会話に化けたり、一方が失敗したりしない）。
- [ ] AC6: 保存されていた識別子が無効・失効している（該当する会話が見つからない）場合でも、
  pane が `failed` にならず、通常のシェルとして使える状態になる。
- [ ] AC7: 連携の有効化・無効化・状態確認が、ブラウザのリロード後も正しい状態を保持している
  （設定はサーバ側に永続化される。既存のブラウザ単位の設定とは異なる範囲——非機能要件参照）。
