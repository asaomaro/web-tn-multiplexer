# 決定記録

## D1: 作成では名前を決めてから予約と起動へ進む（design の点検 1 ラウンド目の代案を 2 ラウンド目で取り消した）

- 背景: design の点検 1 ラウンド目が、`createWorkspace` の予約の前に await を足すと `placeFor` の注記の不変条件（起動までを同期で進める）と食い違うと
  指摘し、「名前を決める処理を起動と並べ、commit の直前に await する」代案を示した。いったんそれを design D4b にした。
- 決定: 2 ラウンド目の点検が、その形では起動の成功（`wireExit` を付けた後）から commit までの間に await が入り、その間にシェルが終わると
  `closePaneAfterExit` が pane をモデルに見つけられず（`SessionService.ts:436`）、commit の後に死んだ pane が running のまま残ると指摘した。
  そこで**名前を決めてから予約と起動へ進む**形に戻した（design D4b）。名前を渡したとき（worktree）は await しない。
- 理由 / 代替案: 起動を同期で進める不変条件が前提にしているのは分割の孤児のテストで、workspace の作成を通る既存のテストは結果を await している。
  待ちが増えるのは名前を決める時間（ふつう数 ms、上限 200ms）だけ。退けた案：上限 < 猶予を構成で保証する——テストは猶予を 5ms に差し替えるので
  成り立たず、本番でも値の組み合わせに暗黙に依存する。
- 影響: coding（T4）で、既存の起動の順序のテストが落ちないことを確かめる。

## D2: 自動の名前の workspace で変えずに確定しても、付けた名前にしない（herdr の workspace と違う）

- 背景: herdr の画面は、workspace の名前を変えずに確定すると自動の名前をそのまま付けた名前として固定する（`overlay_input.rs:955`・
  `app/api/workspaces.rs:115`）。tab は変えていなければ送らない。
- 決定: 本製品は tab の規則（と新しい tab の D75）にそろえ、変えずに確定したら送らない（requirements・design D7）。herdr との違いとして対応表に書く。
- 理由: 名前のダイアログは今の名前を全選択で開くので、Enter を押しただけで以後自動の名前が追従しなくなるのは気づきにくい。

## D3: T10（テストの実行と記録）は test 工程で消化し、E2E の一式は deliver の直前に回す

- 決定: T10 は coding の承認時に未チェックのまま残し、test 工程で単体一式と影響を受ける E2E の spec を走らせて記録する。E2E の一式は deliver の直前に 1 回
  （利用者の指示「少しの修正ですべて回すのは時間とみあいません」）。
- 理由: `aidev-30-tasks` 手順6。前の work（`20260921-new-terminal-cwd` の decisions D6）と同じ扱い。

## デバッグ D1: review の原因究明を省いた（2026-09-21T09:09:35Z）
- 背景: review の差し戻しが 3 回（上限 3）。
- 決定: 原因究明（aidev debug start）の委譲を省いた。
- 理由: 原因は特定済み：ラウンド 3 の should は文書（既知の制約）の書き方の範囲の不足で、コードの欠陥ではない。nit も順序・ログ・注記の小さな直しで、どれも再現と修正の方法が指摘に書かれている

## D4: 止まった問い合わせが返るまではほかの場所もフォルダ名・復元は合計 1 秒を過ぎたら残りをフォルダ名（受け入れた割り切り。review ラウンド 1〜3）

- 背景: requirements の非機能要件は、名前を決める待ちが上限を超えたときの例外を「その場所のフォルダ名」とだけ定めている。review ラウンド 1・2 で、
  応答しない fs（止まった NFS 等）への stat は待つのをやめても取り消されず libuv のスレッド（既定 4 本）を塞ぐこと、1 つずつ決める復元は遅いだけの fs でも
  数に比例して `/ws` の受け付けを遅らせることが分かり、design の「振る舞いの詳細」（「復元」「上限を超えた後」）に対策を入れた。その結果、フォルダ名に
  なる範囲がその場所より広がった。ラウンド 3 で、この広がりが decisions に無く、test-result が AC1・AC6 を無条件に pass としていたと指摘された。
- 決定: 次の 2 つを、requirements の例外より広い**受け入れた割り切り**とする。
  ① 上限を超えた問い合わせが返るまでの間は、**どの場所でも**（ローカルの正常なリポジトリでも）作成・名前を空にして確定・復元の自動の名前を、根を探さず
  フォルダ名にする（`SessionService` の `labelLookupsStuck`）。遅いだけなら返った時点で元に戻り、止まったままなら戻らない。
  ② 起動時の復元は、名前を決めるのに合計 1 秒（`RESTORE_LABEL_BUDGET_MS`）を過ぎたら残りをフォルダ名にする（止まっていなくても遅いだけで起きる）。
  どちらもログに出し（`workspace label lookup timed out`・`workspace label lookup over restore budget`）、付いたフォルダ名は自動の名前のままにする——fs が
  応答するようになってから名前を空にして確定すれば決め直す。見え方と戻し方は `docs/verification.md` の「既知の制約」に書く。
- 理由 / 代替案: 止まった stat を重ねると、サーバ全体のファイルの読み書き（静的ファイルの配信・`session.json` の保存）まで止まる——名前がフォルダ名に
  なるより重い。退けた案：止まった場所（cwd）だけをフォルダ名にする——同じ止まったマウントの別の場所を区別できず（どのマウントかを知るにはまた fs に
  問い合わせる）、そこへの stat がまたスレッドを塞ぐ。1 度上限を超えたら 60 秒根を探さない冷却（ラウンド 1 の直し）——遅いだけの fs でも全部の場所を
  フォルダ名にしたので、返るまでだけに狭めた（ラウンド 2）。復元に合計の期限を置かない——workspace の数に比例して `/ws` の受け付けが遅れる。
- 影響: AC1・AC2・AC4・AC6 は「fs が止まっている・遅い間を除く」条件つきの pass とする（`test-result.md`。AC2・AC4 は review ラウンド 4 で足した）。design の「振る舞いの詳細」の「上限を超えた後」から
  この D4 を指す。
