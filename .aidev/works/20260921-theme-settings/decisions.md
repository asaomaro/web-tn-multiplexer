# 決定記録

## D1: dracula のアクセントを、上に載る文字が 4.5:1 に届くまで暗くする

- 背景: 今のアクセント #6272a4 の上の文字 #f8f8f2 は 4.41:1（`MobileShell.vue:153-155` の「この端末に合わせる」の押された状態・
  `ExtraKeys.vue:133-135` の押された修飾キー）。requirements の非機能要件は「dracula＝今の色、ただしコントラストを満たさない箇所は
  コントラストを優先して直し、decisions に残す」。
- 決定: dracula の `--wtm-accent` を `ensureContrast("#6272a4", ["#f8f8f2"], 4.5, "#000000")` の値 **#6070a1**（2% 黒へ。各成分は四捨五入。
  比 4.55）にする（色相は同じで、わずかに暗い）。dracula の正は `uiTokens.ts` の定数で、この値を直に書く。
- 理由 / 代替案: 文字の色を変える案は、ほかの全ての場所の文字に波及する。アクセントは 2 か所の押された状態の下地だけ。
- 影響: dracula の見た目が変わるのはこの 2 か所の押された状態の背景だけ。

## D2: `.goto-picker-meta` の透明度を 0.6 から 0.7 にする

- 背景: goto の一覧の補足の文字は 0.6 に薄めてあり、選ばれた行の背景 #44475a の上で 4.27:1（`GotoPicker.vue:392-395`）。
  WCAG 1.4.3 の 4.5:1 を割る。ほかの薄めた文字は 0.7 以上（無効な部品の 0.4・0.5 は対象外）。
- 決定: 0.7 にする（dracula で 5.18:1）。全テーマで「0.7 に薄めても 4.5:1」を文字の色の条件にする（design の表）。
- 理由 / 代替案: 薄めた文字用の色の変数を足す案は、透明度の違う 15 か所を 1 色にまとめることになり、dracula の見た目が広く変わる。
- 影響: goto の一覧の補足の文字が少し濃くなる（全テーマ）。

## D3: `color-scheme` を当て、dracula でもブラウザ標準の部品を暗く描かせる

## D4: 入力欄の枠は「テーマの色で描いて全テーマを単体で確かめる」から「ブラウザが描いた枠を E2E で測る」に改める

- 背景: requirements の AC9 は入力欄の枠をテーマの色で描く前提だったが、入力欄は前 work の方針で UA の既定の見た目のまま
  （`SettingsDialog.vue:427-428` の注記：背景を透かして枠を薄くすると欄であることが分からなくなる）。
- 決定: 入力欄の枠と、設定ダイアログの部品（`<select>`・切り替え・ラジオ）の UA の既定のフォーカスの枠は `color-scheme` に任せてブラウザに
  描かせ、暗いテーマ・明るいテーマ各 1 つで、Chromium が描いた枠の色と隣の色の比が 3:1 以上であることを E2E で測る。requirements の AC9 を
  そのように改めた。
- 理由 / 代替案: 全ての入力欄に枠の色を書く案は、前 work の判断（UA の既定のまま）を覆し、入力欄ごとの見た目の調整が要る。
- 影響: ブラウザごとの描き方の違い（Firefox・Safari）は E2E の対象外で、`docs/verification.md` の手で確かめる項目に入れる。

## D5: 端末の配色は上流の値に 2 つの規則を当てる（選んだ文字の色・カーソルの色）

- 背景: 配色集の `selectionBackground` は選んだ文字を反転させる端末の前提の値を含み、xterm.js ではそのままだと選んだ文字が背景に溶ける
  （research F10：catppuccin 1.14・nord 1.17・gruvbox-light 1.00・kanagawa 1.00・kanagawa-lotus 1.00）。カーソルが背景とほぼ同じ明るさの
  テーマもある（F11：catppuccin-latte 2.34・one-light 1.82）。requirements は「端末の色は上流の値」。
- 決定: (a) 文字と選択の色の比が 3 未満で、背景色と選択の色の比のほうが大きければ `selectionForeground` に背景色を入れる（上の 5 つ）。
  (b) カーソルと背景の比が 3 未満ならカーソルを文字の色にする（上の 2 つ）。16 色・背景・文字・選択の背景は上流のまま。規則は protocol の
  `finalizePalette` の 1 か所。requirements のスコープに書き戻した。
- 理由 / 代替案: 選択の背景を herdr の `selection_bg` に替える案は上流の見た目から離れる。反転は上流の端末がしている描き方そのもの。
- 影響: 該当テーマの選択とカーソルの見え方が上流の端末（iTerm 等）に近づく。サーバの OSC 12 の答えも直したカーソルの色になる。
  tokyo-night-day は文字と選択の比が 2.49 で 3 を割るが、背景と選択の比 1.81 のほうが悪く、反転しても良くならないので上流のまま残す
  （全テーマの比は research F10）。

## D6: AC9 の対象外を「無効な部品」から「無効な部品・操作できない項目の表示・記号を切にしたときの状態の丸」に広げる

- 背景: 薄めて描く箇所（research F40）には、無効な部品（0.4・0.5）のほかに、ヘルプの「未対応」の行（`HelpDialog.vue:290-291` の 0.5。
  操作できない項目の表示）と、状態の記号の 0.3 の丸（`StateIcon.vue:79-88`。エージェントの居ない行の飾りと、記号を「切」にしたときの
  unknown）がある。
- 決定: どちらも AC9 の対象外にする。「未対応」の行は WCAG 1.4.3 の inactive user interface component の例外に準じる（操作できないことを
  示す薄さそのものが情報）。状態の丸は、エージェントの居ない行は情報を持たない飾り、記号の「切」は利用者が色だけの表示を選んだ場合で、
  AC9 は既定の「入」で判定する。requirements の AC9 の括弧書きに書き戻した。
- 理由 / 代替案: 透明度を上げる案は、未対応の行・状態の無い行を通常の行と見分けにくくする。
- 影響: 単体テストの検査の相手にこれらは入れない。

## D7: 操作の時刻（`lastInteractionAt`）を、サイズを決める資格を問わず進める

- 背景: design D6 の答えの 2 段目は「その tab を表示していてテーマを伝えた人のうち、最後に操作した人」を `ClientRecord.lastInteractionAt` で選ぶ。
  ところがこの値は `SizeAuthority.noteInteraction` が資格の判定（`canDecideSize`）の**後**でしか進めておらず、fit していないモバイルは接続した
  時刻のまま——2 段目が効くのは主にそのモバイルだけが見ている場合なので、2 台いると「最後に接続した人」で選んでいた（T5 のタスク点検で発見）。
- 決定: `noteInteraction` で `touch` を資格の判定の前に移す。
- 理由 / 代替案: `lastInteractionAt` を読むのはほかに `transferOwnership`（`SizeAuthority.ts:130-140`）だけで、候補を `canDecideSize` で絞ってから
  比べるので、権限の移り方は変わらない。近似のまま残して文書に書く案は、AC8 の「最後に操作したもの」と合わない。
- 影響: tasks の T5 の対象に `SizeAuthority.ts` が加わった（負の対照は `nc-T5.txt`）。

## D8: 答えの引き方に「テーマを伝えた全クライアントのうち最後に操作した人」の段を足す

- 背景: 新しい pane はシェルを起動して猶予（`SessionService.ts:33` の 300ms）を待ってからモデルに入る。その間も Mirror は PTY の出力を受けて
  問い合わせに答えるが、`getPane` が引けないので design D6 のままでは dracula で答えていた。新しい tab も、`client.view` が届くまで誰も見ていない
  ので同じ。シェルの起動設定や起動直後のアプリが OSC 11 で明暗を調べると、**明るいテーマの人が作った pane でも暗い背景の答え**になる
  （requirements の背景 4 が避けたい状態。T7 のタスク点検で発見）。
- 決定: pane・tab が引けないとき、またはその tab に答えられる人（権限者・表示している人）がいないとき、テーマを伝えた全クライアントのうち
  `lastInteractionAt` が最新のものの配色で答える（ふつうは作った本人。作る操作の直前に入力している）。それも無ければ dracula。design D6 と
  requirements の AC8 に書き戻した。
- 理由 / 代替案: 猶予の間だけ作った人を覚えておく案は、SessionService から TerminalManager へ作った人を渡す口が要る。既知の制限として残す案は、
  AC8 の目的（アプリが明暗を正しく選ぶ）を新しい pane で満たさない。
- 影響: どの tab でも見られていない pane の問い合わせも、最後に操作した人の配色で答える（以前は dracula）。負の対照は `nc-T5.txt`。

## D9: 再接続の表示の幕（`--wtm-backdrop-strong`）を、明るいテーマでは白い幕にする

- 背景: design の表は幕を全テーマ黒（0.5）にしていたが、再接続の表示（`ReconnectOverlay.vue` の「接続中…」「つながるまで入力できません」）は
  パネルでなくこの幕の上に `--wtm-fg` で文字を直に描く。明るいテーマの文字は暗いので、黒で暗くした端末の背景の上では題が 3.2〜3.5、0.85 に
  薄めた注記は 2.7〜2.9 で、AC9 の 4.5 に届かない（T10・T9 のタスク点検で発見）。
- 決定: 明るいテーマの `--wtm-backdrop-strong` を `rgba(255, 255, 255, 0.6)` にする（暗いテーマと dracula は黒 0.5 のまま）。検査に「fg を 0.85 に
  薄めて、端末の背景・bg・menu-bg に幕を重ねた色の上で 4.5」を足した。design の表に書き戻した。
- 理由 / 代替案: この幕はダイアログを浮かせる用途ではない（ダイアログは `--wtm-backdrop`）ので、research の「黒い幕は明るいテーマでも浮かせる」と
  衝突しない。題と注記をパネルの中へ入れる案は、再接続の表示の見た目が全テーマで変わる。
- 影響: 明るいテーマでは再接続の間、端末が白く霞む（暗いテーマは暗く沈む。今と同じ）。dracula の見た目は変わらない。負の対照は `nc-T10.txt`。

## D10: ブロックカーソルの下の文字の色（`cursorAccent`）を背景色にする規則を足す

- 背景: xterm.js はブロックカーソルの下の文字を `cursorAccent` で描き、無ければ固定の `#000000` を使う（`@xterm/xterm` の `ThemeService.ts`）。
  design D2 はこれを扱っておらず、明るいテーマ（暗いカーソル）ではカーソルの下の文字の比が one-light 1.51・gruvbox-light 1.81 など 3 未満だった。
  規則 (b) でカーソルを文字の色にした one-light・catppuccin-latte では、かえって悪くなっていた（T12 のタスク点検で発見）。
- 決定: `finalizePalette` の規則 (c) として `cursorAccent` を背景色にする（dracula は今の xterm.js の既定のまま）。規則 (b) でカーソルと背景の比が
  3 以上なので、カーソルの下の文字も 3 以上になる。web の `toXtermTheme` は持っていれば渡す。
- 理由 / 代替案: 上流の端末（iTerm 等）もカーソルの下は背景色で描く。
- 影響: dracula 以外の 16 テーマのカーソルの下の文字が背景色になる。負の対照は `nc-T12b.txt`。

## D11: テーマの欄を表示の節の中ではなく、独立した節「テーマ」（通知と表示の間）に置く

- 背景: design は「表示の節の先頭に `<fieldset>`」だったが、既存の単体テストと E2E は「表示の節の切り替え・注記は 1 つ」を前提に
  `section[aria-labelledby="settings-display"] [role="switch"]` で探している（`SettingsDialog.test.ts:277`・`:372`・`:382`、
  `SettingsDialog.symbolsNote.test.ts:21`、`settings.spec.ts:191`・`:252`）。テーマの欄には切り替えと注記があり、表示の節に入れると
  既存の探し方が別の部品を掴む。
- 決定: 見出し付きの節「テーマ」を通知と表示の間に足す（節は 4 つ）。節の並びを確かめるテスト（単体と `settings.spec.ts` の 3 か所）を 4 節に直す。
- 理由 / 代替案: 既存の探し方を全部書き換える案より変更が小さい。テーマは表示と別の話題（配色）で、見出しで探せる。
- 影響: 設定ダイアログの節が 4 つになる（前 work の D7 の「3 節」から増える）。

## D12: AC-I5 のスクロールの位置は、`.xterm-viewport` の `scrollTop` ではなくスクロールバーのつまみの位置で見る

- 背景: design の AC-I5 の対応は「`.xterm-viewport` の `scrollTop` を前後で比べる」としていたが、xterm.js 6 はスクロールを自前のスクロール可能な要素で
  扱い、`.xterm-viewport` の `scrollTop` はホイールで遡っても 0 のまま（T18 のタスク点検で実験して確かめた。つまみは 305px → 278px と動いた）。
- 決定: E2E は `.xterm-scrollable-element .scrollbar.vertical .slider` の `style.top` を、描画の 2 回分を待ってから前後で比べる。
- 理由 / 代替案: xterm.js の内部（`buffer.active.viewportY`）はページから触れない。つまみの位置はブラウザの DOM で、利用者が見るもの。
- 影響: design の AC-I5 の記述と E2E の手段が違う（この記録で追える）。

## D13: 答えに使う「最後に操作した時刻」を別に持ち（接続しただけでは 0）、作る操作の前にも進める

- 背景: design D6 の 2 段目・3 段目は「最後に操作した人」を `ClientRecord.lastInteractionAt` で選んでいたが、(1) この値は接続した時刻から始まる
  ので、一度も操作していない後から来た（再接続した）クライアントが、先に操作した人に勝っていた。(2) 作る操作（`tab.create`・`workspace.create`）は
  この値を進めず、`pane.split` も起動の猶予の後に進めるので、decisions D8 の「作った本人に当たる」が成り立っていなかった（cross の点検で発見）。
- 決定: `ClientRecord.lastActedAt`（初期 0。`touch` で進む）を足し、答えはこれで選ぶ。`tab.create`・`workspace.create`・`pane.split` の受け口は、
  作る前（`await` の前）に `touch` する。`transferOwnership` の並びは今の `lastInteractionAt` のまま。
- 理由 / 代替案: `lastInteractionAt` の初期値を 0 にする案は、権限の移譲の並び（`SizeAuthority.ts` の `transferOwnership`）を変える。
- 影響: 作る操作が権限の移譲の並びでも「操作」に数えられる（`touch` は両方を進める）。負の対照は `nc-cross.txt`。

- 背景: review ラウンド 1。(1) 選ばれている pane の枠（`PaneFrame.vue` の `.pane-frame-edge-current`）は `--wtm-menu-border`＝herdr の `surface0` で描いており、
  明るいテーマなどで周りの背景とほぼ同じ明るさだった（one-light 1.00・solarized-light 1.04・rose-pine 1.13）。前の work（20260920-ui-selection-visuals の
  US3・AC4）の「入力先の pane を枠で知る」が成り立たない。(2) 選択の面（`--wtm-menu-active-bg`）と枠の背景の比が one-dark・rose-pine で 1.07 と低く、
  表示中の tab・サイドバーの行・goto とメニューで選んだ項目が見分けにくかった（dracula は 1.56）。
- 決定: `--wtm-pane-current` を足し、dracula 以外は背景と端末の背景に対して 3:1 に寄せる（WCAG 1.4.11。状態の印）。dracula は今の #44475a のまま
  （1.79。requirements の AC9 の列挙に無く、既定の見た目を変えない）。選択の面は枠の背景に対して 1.5 以上に寄せ（`MIN_SELECTED_SURFACE_RATIO`）、
  hover はそれと枠の背景の中間。枠の線（`--wtm-menu-border`）は herdr の `surface0` のまま（区切りの線は飾り）。全テーマを単体テストで確かめ、

## D16: サイドバーの 2 行目は行ごとではなく補足の文字だけを薄め、警告（未検証）は薄めない

- 背景: review ラウンド 2。警告の文字 `--wtm-warn-fg` は不透明のまま 4.5 に寄せていたが、サイドバーの 2 行目（`.sidebar-row-line2`）が行ごと
  `opacity: 0.75` だったので「未検証」も薄まり、明るいテーマなど 8 テーマで枠の背景（menu-bg）の上 3.84〜4.34、hover の上では 13 テーマが 4.5 を割った。
  「未検証」が出るのは agents の行だけで、その行は選ばれている行（`sidebar-row-current`）にならないので、下地は menu-bg と hover の 2 つ。dracula の
  #ffb86c は 0.75 に薄めても menu-bg（#282a36）の上 5.39・hover（#343746）の上 4.63 で、以前から 4.5 を満たしていた（review ラウンド 3 で測り直した。
  以前の記述の訂正は review.md のラウンド 2 の対応に残した）。
- 決定: 薄めるのを行から子の `span`（ブランチ名・数・エージェント名）へ移し、警告だけ `opacity: 1` にする。**全テーマで同じ規則にし、警告を本文より
  薄くしない**。dracula の「未検証」が以前より濃くなるのは、コントラストのための直しではなく、規則をそろえるための意図した例外（requirements の
  非機能要件・AC4 の「今と同じ見た目」の例外として記録する）。警告の色は不透明で 4.5 に寄せたまま、値は変えない。design の表で選択の面（active）の
