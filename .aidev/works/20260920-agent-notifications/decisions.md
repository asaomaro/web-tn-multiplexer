# 決定記録

## D1: `prefix+o` で対象が消えていたら、捨てて次へ進む（herdr とは逆）

- 背景: herdr は対象が到達不能なとき「利用できません」と出して**通知を消費せずその場に残す**
  （`herdr:src/client/shell/notification_policy.rs:69-76`。research F58）。
- 決定: **その 1 件を捨てて次へ進む**。全部消えていたら「知らせの対象はすでに閉じられています。」を
  1 回だけ出す。
- 理由 / 代替案: **herdr のトーストは 5〜8 秒で自動的に消える**（research F59）ので、留めても
  そのうち片付く。**この製品のトーストは消えない**（requirements）ので、留めると
  **待ち行列が永久に詰まり、後続の知らせに `prefix+o` で辿り着けなくなる**。
- 影響: AC11 の文言と回数が herdr と違う。E2E の期待値もこちらに合わせる。

## D2: 設定の切り替えは `<button role="switch" :aria-checked>` にする

- 背景: この製品の既存のトグルは**すべて `<button :aria-pressed>`**（research F20・F91）。
  `role="switch"` も `<input type="checkbox">` もリポジトリに 0 件。
- 決定: **`role="switch"`** を使う。
- 理由 / 代替案: APG は switch を「on/off を表し、**操作が即座に効く**もの」と定義しており
  （research F89）、AC-I2（押した時点で反映・確定ボタンを置かない）と一致する。
  既存の `aria-pressed`（`ExtraKeys`・モバイルの fit ボタン）は**道具のモード**であって設定ではない。
  `<input type="checkbox">` はフォーム確定の含みがあり、この製品の流儀から最も遠い。
- 影響: **本製品で最初の設定面なので、ここが以後の基準になる**。
  backlog「外観と設定」がこのダイアログを育てるときも switch に揃える。

## D3: 案内は「既にフォーカスがあればその場で出す」（requirements の上書き）

- 背景: requirements は「**知らせが起きた瞬間には出さない**」と定めた——最初の知らせは定義上
  「フォーカスが無いとき」に起きるのが普通で、その場で出すと**誰も見ていないタブに出て
  そのまま消費される**ため。
- 決定: **判定した時点で既にウィンドウにフォーカスがあるなら、その場で出す**。
- 理由 / 代替案: 表の (b)（フォーカス有り・その pane は非表示）で最初の出来事が起きると、
  **`window` の `focus` はもう発火しない**ので、`focus` だけを契機にすると
  **利用者が一度離れて戻るまで案内が出ない**。要件がそう書いた懸念（見ていないタブに出る）は
  **フォーカスがある場合には当たらない**ので、この条件でだけ上書きする。
- 影響: AC5 の検証手順が 2 通りになる（フォーカス無しで起きた場合／有りで起きた場合）。

## D4: 待ち行列に入る条件は、トーストの入／切とは独立

- 背景: requirements は「**待ち行列と、この work のトーストは 1 対 1**」と書いた。
- 決定: **待ち行列に入るのは「表の (c)（その pane を見ている）ではないとき」**で、
  **トーストが出たかどうかとは独立**。`QueuedNotification.toastId` は `number | null` にする。
- 理由 / 代替案: 3 経路は独立に入／切できる（AC6）ので、**トーストを「切」にして OS 通知だけ「入」**に
  した利用者では、1 対 1 を文字どおり守ると**待ち行列が常に空**になり、
  `prefix+o`（AC10・AC11）も OS 通知のクリック（AC15）も効かなくなる。
  requirements が「1 対 1」と書いたのは**どの行が入るか**の話（(a)(b) は入り (c) は入らない）で、
  経路の入／切の話ではない、と読み替える。
- 影響: `drop` は `toastId != null` のときだけ `dismissToast` を呼ぶ。

## D5: 既定値が herdr と違う（トースト 入／OS 通知 切／音 切）

- 背景: herdr の既定は **配送 `Off`・音 `enabled = true`**（research F71）＝「トースト切／音入」。
- 決定: 本製品は **トースト 入／OS 通知 切／音 切**。
- 理由 / 代替案: herdr のトーストは**端末の画面に重なる**ので既定で切にする理由があるが、
  **ブラウザのトーストは画面の隅に出るだけで操作を遮らない**（`Toast.vue` の `bottom:3.5em`）。
  OS 通知は**許可が要る**ので既定で入にはできない（AC7）。音は**環境によって迷惑になる**
  （会議中など。US3）ので切から始める。
- 影響: 既定のままでは席を外した利用者に届かないので、**導線（案内）が必須**になる（AC5・US8）。

## D6: design の 2 巡目の指摘は、再点検せずに直した

- 背景: `maxDocCheckRounds` は 2。design は 1 巡目 14 件（must 7）・2 巡目 13 件（must 5）で、
  **2 巡目の修正を確かめる 3 巡目が無い**。
- 決定: 2 巡目の 13 件を直したうえで design を承認し、**その妥当性の確認は tasks と coding の
  タスク点検・`cross` 点検に委ねる**。
- 理由 / 代替案: 上限を超えて点検を回さない（ハーネスの規約）。2 巡目の指摘は
  **すべて実物の `file:line` で裏が取れており**、修正も同じ根拠に基づくので、
  未検証のまま残る部分は「修正が正しく入ったか」だけ。これは実装時の点検で捕まえられる。
- 影響: **tasks で、2 巡目の修正が集中した箇所（判定済みの寿命・待ち行列の出入り・案内の重複抑止・
  呼び名の組み立て）を別々のタスクに割り、それぞれ独立点検にかける**。

## D7: `TerminalRegistry` に足すのは `isVisible(paneId)` だけ（`visiblePaneIds()` は作らない）

- 背景: design の「対象範囲」の表は `isVisible(paneId)` / `visiblePaneIds()` の 2 つと書いたが、
  **design 本文のどこにも `visiblePaneIds()` の用途が無い**（tasks の独立点検が指摘）。
- 決定: **`isVisible(paneId)` だけ**を公開する。
- 理由 / 代替案: 使わない公開 API を足すと、後から「何のためにあるのか」が分からなくなる。
  必要になった時点で足せばよい（`visible` は既にあるので足すのは 1 行）。
- 影響: design の表の表記は過剰。**tasks（T8）が正典**。

## D8: `prefix+o` で捨てた件があれば、移れた場合でも必ず知らせる

- 背景: D1 で「対象が消えていたら捨てて次へ進む」と決めたが、**実装は全件が到達不能だったときにしか
  文言を出していなかった**。review ラウンド1 の指摘——後ろに到達できる件があると、
  **「1 回押しただけでトーストが何枚も消えて別の pane に着いた」ように見える**。
  requirements の AC11 は「先頭の pane が既に無ければ、**その旨を出して**次の件へ進む」と書いている。
- 決定: **捨てた件が 1 つでもあれば、移れたかどうかに関わらず 1 回だけ知らせる**
  （捨てた件数ぶん繰り返さない）。文言は「知らせの対象はすでに閉じられていました。」。
- 理由 / 代替案: 件ごとに出すと、8 件全滅のときに 8 枚出て邪魔になる。出さないと AC11 を満たさない。
  **「1 つでもあれば 1 回」**が両方を満たす最小の形。
- 影響: `test-result.md` の AC11 の判定は、この修正の後のものに更新した。
  **design「振る舞い 6」の「全部消えていた場合は 1 回だけ出して終わる」は、この決定が上書きする**
  （D7 と同じ扱い。**tasks と実装が正典**）。あわせて、同じ状況の文言が `prefix+o` と［移動］で
  割れていたのを定数に 1 本化した（review ラウンド2）。

## D9: 知らせのトーストに［移動］のボタンを置く

- 背景: review ラウンド1 の価値適合の指摘（US4）。**既定では OS 通知が「切」**なので、
  知らせから対象へ移る手段が `prefix+o` しか無い。しかも**トースト本体のクリックは「消す」**なので、
  **「知らせをクリックする」という最も自然な操作が、対象へ行くどころか行き先ごと捨てる**。
  モバイルはサイドバーも無く、`prefix+o` はソフトキーボードの Prefix ボタン経由になる。
- 決定: 知らせの `sticky` トーストに **［移動］のボタンを 1 つ**置き、`focusNotification(key)` を呼ぶ。
- 理由 / 代替案: 本体のクリックを「移動」に変える案は、既存のトーストの流儀（クリックで消す）を
  この work だけ変えることになり、閉じる手段も失う。**ボタンを足すほうが既存を壊さない**
  （仕掛けは案内のために既に作ってある）。
- 影響: マウス／タッチ主体の利用者にも US4 が既定で成立する。

## D10: 音が「この環境で使えない」と「いま鳴らせない」を分ける

- 背景: `SoundPort` は `"played"` / `"blocked"` / `"unsupported"` を返すのに、
  実装は `soundBlocked = r === "blocked"` で **`"unsupported"` を `false` に畳んでいた**。
  結果、`AudioContext` が無い環境で**音の行が「入」のまま注記も出ず、
  永久に鳴らない設定を利用者が「入」だと思い続ける**（design の異常系の表はこの行を定めていた）。
- 決定: `soundUsable`（環境の性質。一度立てたら下ろさない）を足し、
  設定では `disabled` ＋「この環境では音を鳴らせません」を出す。
  `soundBlocked`（いま鳴らせない。操作すれば鳴る）とは別に持つ。
- 理由 / 代替案: 1 つのフラグに畳むと、利用者に出す理由が「どちらか分からない」ものになる。
  **理由が違えば打つ手も違う**（片方は諦める、もう片方は画面を触れば直る）。

## D11: `ActionDispatcher` の `notifications` を必須にする

- 背景: review ラウンド1 の指摘。省略可にしていたので、**結線を落とすと `prefix+o` が完全に無反応**になる
  （requirements は「キーを押したのに無反応を作らない」と書いている）。同じ「結線を落としても黙って壊れる」
  問題を、`NotificationSettingsDialog` では **must として throw に倒した**のに、ここは逆の扱いだった。
- 決定: **必須にする**。落とした時点で型エラーになる。
- 理由 / 代替案: 実行時に投げる案（ダイアログと同じ）もあるが、`ActionDispatcher` は
  **組み立て時に全部そろう**部品なので、**型で塞ぐほうが早く気づける**。
- 影響: テストの生成箇所 7 つに no-op のスタブを渡した（結線の有無はそれらのテストの関心ではない）。
