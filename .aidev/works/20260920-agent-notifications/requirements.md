# 要件: エージェントの「入力待ち」「完了」を、画面を見ていなくても知らせる

## 背景 / 課題

本製品の目的は **複数のエージェントを 1 画面で見張ること**だが、**見張れるのは画面を見ている間だけ**である。

- 別のタブ・別のアプリへ移ると、エージェントが入力待ちになっても完了しても**何も起きない**。
  `Notification`・`Audio`・`vibrate` の呼び出しはリポジトリ全体に 1 つも無い（点検が grep で確認）。
- サイドバーの状態の点（`displayStateFor`。`packages/web/src/store/seen.ts:57-61`）は既にあるが、
  **そのサイドバーが見えていないときには役に立たない**。
- 既存のトーストは**ページ内にしか出ず 4 秒で自動的に消える**
  （`packages/web/src/components/Toast.vue:12` `AUTO_DISMISS_MS = 4000`）。
  席を外している利用者には届かない。
- `prefix+o`（herdr の「通知の対象へ移動」）は `{ type: "notYet", work: "通知" }` のまま
  （`packages/web/src/keys/keymap.ts:16`）。

結果、**エージェントが入力待ちで止まったまま時間が過ぎる**。これは「複数を並行して回す」という
使い方そのものを損なう——人間が定期的に画面を見に戻らないと、並行度が上がらない。

herdr は同じ問題を `ui.toast.delivery`（`off` / `herdr` / `terminal` / `system`）と `ui.sound.*` で扱う。
**本製品はブラウザなので、herdr が苦労している部分（外側端末への委譲）が要らず、OS 通知に素直に繋がる**。

出自: backlog `product-roadmap.md` の「通知: 完了・入力待ちのアプリ内トースト / OS 通知（HTTPS・PWA 前提）/ 音、
通知の対象への移動（herdr prefix+o）」。**着手の理由**（herdr の設定 132 項目のうち本製品で最も価値が高いと
判断した経緯）は、この work の `research.md` に調査として残す。

## 既存の実装で、この要件が前提にしている事実

**requirements の独立点検（ラウンド1）で、当初の前提が 1 つ誤っていたことが分かった**ので明記する。

- **`shouldMarkSeen(paneVisible, windowFocused)` は定義されているだけで、本番の経路から一度も呼ばれていない**
  （`packages/web/src/store/seen.ts:80-82`。呼び出しは `seen.test.ts` のみ）。
- 実際の既読は `packages/web/src/main.ts:184-191` の `markVisibleAgentsSeen`——**pane の表示を一切見ず**、
  「ウィンドウにフォーカスがあれば session の全 pane を既読にする」。
  コメントに「意図的な簡略化」と明記されている（`main.ts:178-183`）。
- **帰結**: ウィンドウにフォーカスがある間は `completionSeq` の前進が即座に既読化されるので、
  **`displayStateFor` は `done` を返せない**。「フォーカスはあるが、その pane は見ていない」状態で
  完了を知らせることは、既読（`seen`）を使う限り**原理的にできない**。
- したがって**この work は既読とは別に「知らせたかどうか」を持つ**（下記スコープ）。既読の意味論は変えない。

その他の前提（点検で確認済み）:

- 再接続のたびに `client.hello` → `applySnapshot` が **pane を丸ごと置き換える**
  （`packages/web/src/store/StoreAdapter.ts:29-38`）。`Connection` は自動で再接続する。
- サーバ側に**揺れ対策が既にある**: `AgentTracker` の起動猶予 3 秒・working→idle の保留 700ms×3
  （`packages/server/src/agent/AgentTracker.ts:27-31` `:133-140`）。**保留があるのは working→idle だけで、
  `blocked` には無い**（`:135-136`）。
- `wtm.prefs.v1` の書き込みは `JSON.stringify({ agentSort: v })` で**オブジェクト全体を置き換える**
  （`packages/web/src/store/view.ts:56-62`）。同じキーに足すだけでは、並び順を切り替えた瞬間に消える。
- `MobileShell` は `Sidebar` を描かない（`packages/web/src/App.vue:42-46`）。上部バーは 3 ボタンのみ
  （`packages/web/src/mobile/MobileShell.vue:80-84`）。`Toast` と `ContextMenu` は分岐の外なので
  **モバイルでもトースト自体は出る**（`App.vue:67-75`）。
- 全体メニューは APG の Menu で、項目は `{label, run}`、キーは ↑↓/Enter/Space/Esc のみ——**Tab を扱わない**
  （`packages/web/src/components/ContextMenu.vue:16-19` `:108-129`）。

## 目的 / ゴール

**画面を見ていなくても、手が要るエージェントに気づける状態**。具体的には:

- エージェントが**入力待ち**になった／**完了**したとき、その pane を見ていなくても知らせが届く。
- **既定のまま放置しても、利用者が OS 通知に到達できる**（知らせ方の存在に気づける）。
- 知らせから**対象へ一手で移動できる**（探し直さなくてよい）。
- 知らせ方を利用者が選べる（環境によっては音が出せない・通知が邪魔になるため）。

（`charter.md` は無いので紐づけは不要）

## ユーザーストーリー

- US1: 複数のエージェントを並行して回す人として、**別のタブで作業している間に入力待ちになったら知りたい**。
  なぜなら、気づかなければ**エージェントは止まったまま時間が過ぎ、並行して回している意味が無くなる**から。
  （受け入れ: AC1, AC2, AC3, AC5）
- US2: 同じ人として、**長い作業が終わったことを知りたい**。なぜなら、終わっているのに気づかない時間は
  そのまま待ち時間になるから。（受け入れ: AC1, AC2, AC3）
- US3: 同じ人として、**知らせ方を選びたい**（OS 通知／音／アプリ内だけ／切る）。なぜなら、
  会議中は音を出せず、集中したいときは通知そのものが邪魔になるから。（受け入れ: AC6, AC13, AC16）
- US4: 同じ人として、**知らせから対象へ一手で移動したい**。なぜなら、知らせを見てから workspace を
  探すのでは手間が減らないから。（受け入れ: AC10, AC11, AC15）
- US5: 同じ人として、**一瞬だけ状態が変わったものに反応されたくない**。なぜなら、そのたびに通知が出ると
  **通知そのものを無視するようになる**から。（受け入れ: AC4）
- US6: 同じ人として、**同時に何件も起きたとき全部に辿り着きたい**。なぜなら、3 つ並行していれば
  3 つ同時に終わることがあり、**最新の 1 件しか辿れないと残りを取りこぼす**から。（受け入れ: AC9, AC10）
- US7: ブラウザの通知を許可したくない人として、**許可しなくても使えてほしい**。なぜなら、
  許可を強制されるサイトは使いたくないから。（受け入れ: AC7, AC8, AC12）
- US8: 本製品を初めて使う人として、**通知という機能があること自体に気づきたい**。なぜなら、
  設定を自分で探しに行く人は少なく、**気づかなければ無いのと同じ**だから。（受け入れ: AC5）

## スコープ

### 対象

**知らせる出来事**

- pane のエージェントが **`blocked`（入力待ち）に変わった**とき。
- pane のエージェントの **`completionSeq` が前進した**（＝完了した）とき。
  **既読（`wtm.seen.v1`）ではなく、この work が持つ「知らせ済み」で判定する**
  （上記「既存の実装で…」の帰結。既読の意味論は変えない）。

**知らせ方と、その使い分け**（点検の指摘：3 経路で抑止条件が同じだと、前面にいるのに OS 通知が重なる）

| 利用者の状態 | OS 通知 | 音 | アプリ内トースト |
|---|---|---|---|
| ウィンドウにフォーカスが無い | 出す | 鳴らす | 出す（戻ったときに見える） |
| フォーカスはあるが、その pane を見ていない | 出さない | 鳴らさない | 出す |
| その pane を見ている | 出さない | 鳴らさない | 出さない |

- 3 経路はそれぞれ独立に入／切できる（既定: トースト 入／OS 通知 切／音 切）。
- **この work のトーストは自動で消えない**（既存の 4 秒の自動消去とは別扱い）。席を外している間に
  出たものが消えていては意味が無い。消すのは利用者の操作か、`prefix+o` で対象へ移ったとき。

**待ち行列**（herdr の `notification_policy.rs` を参考に、同時多発に耐える形）

- **待ち行列と、この work のトーストは 1 対 1**。上の表で**トーストを出した出来事だけが待ち行列に入る**
  ——(a) と (b) は入り、**(c)（その pane を見ている）は入らない**。見ている pane は
  「後で戻る先」ではないので、`prefix+o` の行き先に並べる意味が無い。
- 未処理の知らせを**最大 8 件**保持する。**9 件目が来たら最も古いものを捨てる**
  （herdr の `notification_policy.rs:50-53` の `pop_front()` と同じ）。
- **同じ pane の古いものは新しいもので置き換える**（同 `:119-132`）。
- `prefix+o` は**先頭を消費して**その pane へ移る（workspace・tab・pane すべてを切り替える）。
  消費された 1 件のトーストも同時に消える。
- **利用者がトーストを消したら、対応する 1 件も待ち行列から消える**（1 対 1 を保つ）。

**設定**

- **メニューの項目から開くダイアログ**として作る（Menu は Tab を扱わないので、切り替えを並べるには
  ダイアログが要る。APG の Dialog）。
- サイドバーの既存の「メニュー」と、**`MobileShell` の上部バー**の両方から開ける。
- **`prefix+s` を割り当てる**。いまは `{ type: "notYet", work: "外観と設定" }`
  （`packages/web/src/keys/keymap.ts:14`）で、**herdr の `settings` と同じ位置**。
  後で「外観と設定」が来たときは**このダイアログを育てればよい**ので、別のキーを作らない。
  `HelpDialog` の記述も合わせる。
- 保存先は `wtm.prefs.v1`（localStorage、ブラウザごと）。**書き込みを併合式に直す**
  ——いまは全置換なので、足すだけでは既存の `agentSort` が消える。

**導線**（点検の must：既定のままでは目的が達成されない）

- **最初に知らせが起きた後、ウィンドウにフォーカスが戻ってから**、「通知を受け取りますか」という
  案内を 1 度だけ出す。**知らせが起きた瞬間には出さない**——最初の知らせは定義上
  「フォーカスが無いとき」に起きるのが普通なので、その場で出すと**誰も見ていないタブに出て、
  そのまま消費されてしまう**（既存の `wtm.hint.prefixHelp.v1` は `Toast.vue:31-39` のとおり
  **pane にフォーカスが入った瞬間**＝利用者が見ている場面で出すので、そこだけ流儀が違う）。
- 案内は**自動で消えない**。「1 度だけ」を消費するのは**利用者が反応したとき**
  （「許可する」か「あとで」のどちらかを押したとき）。無視して放置しただけでは消費しない。

**その他**

- `prefix+o` を `notYet` から置き換える。
- OS 通知のクリックで、そのタブに戻って対象へ移る。
- `docs/herdr-parity.md` の **H29 の行**（「通知（トースト／外側端末／OS／音）」）をこの work の内容に更新する。

### 対象外

- **PWA 化**（Service Worker・manifest・インストール）。ページが開いていれば Notification API だけで
  OS 通知は出せる。**ページを閉じている間の通知**は Service Worker と Push が要るので別 work。
- **通知音の差し替え**（herdr の `ui.sound.path` / `.done_path` / `.request_path`）。内蔵音のみ。
- **エージェントごとの音の切り替え**（herdr の `ui.sound.agents.<agent>`）。
- **herdr の `terminal` 配送**（外側の端末へ委譲）。ブラウザに「外側の端末」が無い。
- **設定画面そのもの**（テーマ・サイドバーの行など）。この work が作るのは**通知の設定だけ**を持つ
  小さなダイアログ。画面全体は backlog「外観と設定」。
- **既読（`wtm.seen.v1`）の意味論の変更**。`markVisibleAgentsSeen` の簡略化はこの work では直さない
  （直すと `done` の表示条件が変わり、サイドバーの見え方に波及する）。**backlog へ送る**。
- **通知の履歴の一覧画面**（待ち行列は持つが、一覧して選ぶ UI は作らない）。
- **サイドバーの点と待ち行列を一致させること**。既読の意味論を変えない以上、**「未処理」が 2 つ併存する**
  ——ウィンドウにフォーカスが戻った瞬間に `markVisibleAgentsSeen` が全 pane を既読にするので
  **サイドバーの `done` の点は一斉に消える**が、この work の消えないトーストと待ち行列は残る。
  戻ってきた利用者には「サイドバーは落ち着いているのに、トーストが何枚も残っている」状態が見える。
  **これを受け入れる**——**残ったトーストと `prefix+o` が「まだ処理していない知らせ」の正典**で、
  サイドバーの点は「いまの状態」を表すものとして別物にする。点の側を合わせるのは既読の意味論の変更なので backlog。
- **サーバ側からの送出**（メール・webhook 等）。

### 先行 work の判断を変える点

`20260920-sidebar-tabbar-controls/requirements.md:79-81` は「herdr の `settings` はメニューに入れない
（この製品に設定画面が無い）」と決め、その判断は `packages/web/src/components/ContextMenu.vue:88-89` の
コメントにも残っている。**この work はその判断を部分的に変える**——メニューに「通知の設定」を足す。
理由: 設定画面が無いことと、**この work が作る機能に設定が要ること**は別の話で、
通知は「入れるか切るか」を利用者が決められないと使い物にならない（US3）。
**足すのは通知の 1 項目だけ**で、テーマ等の一般の設定は引き続き backlog に置く。
`ContextMenu.vue` のコメントもこの判断に合わせて直す。

## 機能要件

- pane のエージェントが `blocked` に**変わった**こと、および `completionSeq` が**前進した**ことを web 側で検知する
  （状態が続いている間は繰り返さない）。
- **初回のスナップショットは基準線にする**（既に `blocked` の pane があっても知らせない。
  ページを開いた瞬間に何件も出さないため）。
- **再接続のスナップショットは、「まだ知らせていない」ものだけを知らせる**。
  知らせ済みのものは繰り返さない。これで **(a) 再接続のたびに一斉に出ることは無く、
  (b) 切断中に `blocked` になって今も `blocked` のものは取りこぼさない**
  ——`Connection` は自動で繋ぎ直す（`net/Connection.ts:401-403`）ので、瞬断での取りこぼしは実際に起きうる。
  **切断中に起きて、再接続までに解消したもの**は知らせない（サーバが履歴を持たないので原理的に不可能）。
- `blocked` は、変化してから既定 **1 秒**状態が保たれたときだけ知らせる。
  完了（`completionSeq`）は**サーバ側に既に保留がある**ので、クライアント側では待たない。
- OS 通知の本文には、**どの workspace のどの pane か**と、**入力待ちか完了か**が分かる情報を載せる。
  同じ pane の通知は**置き換える**（`tag` を使う）。
- `prefix+o` で待ち行列の先頭の pane へ移る。空なら**その旨を出して何も起きない**。
  **対象の pane が既に無ければ**、その旨を出して次へ進む。
  **この 2 つは「操作へのフィードバック」なので、既存の `view.toast()`（4 秒で消えるほう）で出す**
  ——通知の 3 経路の入／切とは**無関係**に必ず出る（キーを押したのに無反応、という状態を作らない）。
  AC5 の案内も同じ扱いで、通知の設定を「切」にしていても出る。
- 設定はサイドバーのメニューとモバイルの上部バーから開ける。

## 非機能要件 / 制約

- **D107 を守る**: 利用者に見せる文言は日本語。サーバの生のメッセージは出さない。
- **既存の操作を壊さない**: 既存のキー・メニューの既存項目の位置と動作が変わらない。
  `wtm.prefs.v1` の既存の値（`agentSort`）が消えない。
- **通知を許可していなくても全機能が使える**（OS 通知だけが使えない）。
- **`Notification` が無い環境でも壊れない**（古いブラウザ・非セキュアな文脈）。
- **音が鳴らせないことがある**: ブラウザの自動再生の制限は**ページの読み込みごと**に利用者の操作を要求する。
  設定が「入」でも、**再読み込み直後にまだ何も触っていなければ最初の 1 回は鳴らない**。
  これを**黙って無視しない**（設定にその旨を出す）。
- 複数のブラウザで同じセッションを開いている場合、**それぞれが独立に知らせる**（設定も既読も
  ブラウザごとなので。`wtm.seen.v1` と同じ流儀）。
- **条項 `e2e-observe-browser` を守る**: 合否はブラウザ側の観測で決める。
  **OS 通知が出たか・音が鳴ったかは DOM から見えない**ので、E2E では**ページ内で `Notification` と
  音の再生を差し替え、呼ばれた事実をページの DOM に残して**そこを観測する
  （テスト自身の WS クライアントで判定しない。固定時間待ちに逃げない）。
- **条項 `regression-negative-control` を守る**: 新機能なので「実装前は要素が無くて落ちる」では弱い。
  **実装後に振る舞いを壊して**落ちることを確かめ、生の出力を `test-result.md` に貼る。

## 相互作用の受け入れ基準（UI を伴う work のみ）

- [ ] AC-I1 開く / 閉じる: 通知の設定は**メニューの項目から開くダイアログ**で、**Esc で閉じる**。
      閉じても設定は保たれる（押した時点で反映済み）。
- [ ] AC-I2 確定 / 取り消し: 各切り替えは**押した時点で反映**（確定ボタンを置かない）。
      取り消しは同じ切り替えをもう一度押す。**閉じるだけで元に戻ることはない**——押した結果が正典。
- [ ] AC-I3 キーボードだけで完結するか: **開くところから閉じるところまでマウス無しで通せる**。
      `prefix+s` で直接開ける。メニュー経由でも通る——**サイドバーの「メニュー」は `<button>` で
      Tab で到達でき**（`Sidebar.vue:149-158`。先行 work の AC-I3 が受け入れ済み）、
      開いた後は ↑↓/Enter でこの項目を選べる。ダイアログの中は Tab で辿れて Space/Enter で切り替える。
      `prefix+o` もキーだけで通る。
      （**1 巡目の要件が「メニュー（マウス）だけ」と書いていたのは誤り**。キーボードから開けないのは
      workspace の**行**の右クリックメニューのほうで、ここではない）
- [ ] AC-I4 フォーカスの行き先: 開いたら最初の切り替えへ移り、閉じたら**開く前の場所へ戻る**
      （既存のダイアログと同じ）。
- [ ] AC-I5 既存の操作を妨げないか: ダイアログの上のキーを端末へ漏らさない。
      この work のトーストは既存のトーストと**同じ場所**に出て、端末の操作を遮らない。
      自動で消えない点だけが違う。
