# 要件: 進行中の保存に相乗りした flush・予約保存が、その後の変更を落とさないようにする

## 背景 / 課題

main で `pnpm -s test` を全体で流したとき、`packages/server/src/composeServer.integration.test.ts` の
「保存した session.json の tab は並べ替えた順（workspace の tabIds の順）」が 2 回中 1 回落ちた。
期待 `["t3","t2"]` に対し、保存された tab は `["t2"]` だけで、直前に作った tab が丸ごと無かった
（`await server.persist.flush()` の直後に session.json を読んで比較している）。

コードを読んで確かめた事実:

- `packages/server/src/session/PersistScheduler.ts` の `DefaultPersistScheduler.flush()` は予約済みのタイマーを
  取り消したうえで `runSave()` を呼ぶ。`runSave()` は**進行中の保存があればその Promise をそのまま返す**（相乗り）。
- 保存の中身は `packages/server/src/composeServer.ts` で `sessionFile.save(toSessionFileData(session))` と組まれており、
  `toSessionFileData(session)` は `save()` を呼んだ時点で同期的に評価される（＝スナップショットは保存の開始時点）。
  `FsSessionFile.save` はそれを `writeFileAtomic` で書くだけ。
- よって、保存が進行中のあいだに行われた変更（tab の作成・並べ替え等）は、その保存にも、相乗りした `flush()` にも
  載らない。しかも `flush()` は予約済みのタイマーを取り消しているので、次の `touch()` が来るまで保存されない。
  タイマー経由（`touch()` → 500ms 後）でも、前の保存が 500ms 以上かかっていれば同様に古い保存に相乗りする。
- 終了時（`composeServer` の `close()`）の `flush()` がこれに当たると、直前の変更が session.json に残らないまま
  プロセスが終わりうる。統合テストでは、全体テストの負荷で保存が遅くなったときにだけ表に出た。

相乗りそのものは「2 つの `save()` が同時に走らない」ための既存の設計（`PersistScheduler.ts` 15-16 行のコメント・過去のレビュー指摘）で、
その性質は失ってはならない。

## 目的 / ゴール

`flush()` が解決した時点、および予約した保存が終わった時点で、**それを要求した時点までの変更がすべて session.json に
書かれている**状態にする。そのうえで、2 つの保存が同時に走ることは今までどおり無い状態を保つ。

## ユーザーストーリー

- US1: wtm を使う利用者として、tab を作った直後にサーバを止めても、その tab が次の起動で復元されてほしい。
  なぜなら、終了直前の操作が黙って失われると、並べた作業環境を作り直す手間がかかるから。（受け入れ: AC1, AC2, AC4, AC6）
- US2: このリポジトリで作業する開発者・AI エージェントとして、全体テストが負荷によって偶に落ちる状態を無くしたい。
  なぜなら、無関係な失敗が混ざると本当の退行を見分けられず、調べ直しに時間を取られるから。（受け入れ: AC5）
- US3: このリポジトリで作業する開発者として、保存の直し方が別の不具合（2 つの保存が同時に session.json を書く・取り消した予約が書かれる・保存が無いときの挙動が変わる）を持ち込まないでほしい。
  なぜなら、同時書き込みは過去のレビューで直した不具合で、取り消しは起動に失敗したときに作りかけの状態を書かないための仕組みだから。（受け入れ: AC3, AC6, AC7）

## スコープ

### 対象

- `DefaultPersistScheduler`（`packages/server/src/session/PersistScheduler.ts`）の保存の直列化の仕方。
- その単体テスト（`PersistScheduler.test.ts`）への回帰テストの追加。

### 対象外

- `PersistScheduler` インターフェース（`touch` / `flush` / `cancel`）の形の変更。
- 保存の中身（`toSessionFileData`・`FsSessionFile`・書き込み方法）の変更。
- 保存の失敗時の再送（今までどおり、失敗は次の `touch()` で改めて保存される扱いのまま）。
- `cancel()` の意味の変更（予約を取り消す＝保存しない、進行中の保存は止めない。追加の保存も「予約」として同じ意味で扱うだけ）。

## 機能要件

- 保存が進行中に `flush()` が呼ばれたら、進行中の保存が終わった後にもう 1 回保存し、その 2 回目が終わってから `flush()` が解決する。
- 保存が進行中に予約の時刻が来たら、進行中の保存が終わった後にもう 1 回保存する。
- 保存が進行中に何度要求（`flush()`・予約の時刻）されても、追加の保存は 1 回にまとめる。
- 保存が進行中でなければ、今までどおりすぐに 1 回保存する。
- `cancel()` は予約（タイマー）に加えて、まだ始まっていない追加の保存も取り消す（「予約を取り消す＝保存しない」という `cancel()` の意味を、追加の保存にも及ぼす）。進行中の保存は今までどおり止めない。

## 非機能要件 / 制約

- 2 つの `save()` が同時に走らない（どの時点でも実行中の `save()` は高々 1 つ）。
- テストは実時間に依存しない（フェイクタイマーと手で解決する Promise を使う）。
- 進行中の保存が失敗しても、その後に要求された保存は行われる（前の失敗で後の保存を落とさない）。

## 完了条件 (受け入れ基準)

- [ ] AC1: 保存が進行中に `flush()` を呼ぶと、進行中の保存の完了後に `save()` がもう 1 回呼ばれ、`flush()` はその 2 回目の完了を待って解決する（2 回目の開始時点で見えている状態が保存される）。
- [ ] AC2: 保存が進行中に予約の時刻が来ると、進行中の保存の完了後に `save()` がもう 1 回呼ばれる。
- [ ] AC3: 保存が進行中に `flush()` を複数回呼んでも（予約の時刻と重なっても）、追加の `save()` は 1 回だけで、どの時点でも `save()` が 2 つ同時に実行中にならない。
- [ ] AC4: 進行中の保存が失敗（reject）しても、その間に要求された保存は行われ、`flush()` はその保存の結果で解決する。
- [ ] AC5: 修正箇所だけを元に戻すと AC1・AC2・AC4 の新しいテストが落ちる（負の確認）。AC3・AC6・AC7 は修正前から成り立つ性質（同時に走らない・保存が無いときはすぐ保存・予約の取り消し）が保たれることの確認なので、負の確認の対象外とする。修正後は `pnpm -s test` を全体で 2 回流して 2 回とも通る（元の失敗は負荷次第で出る偶発的なもので、2 回の通過は直った証明ではなく退行が無いことの確認。直ったことの根拠は AC1・AC2 の決定的な単体テストと負の確認に置く）。
- [ ] AC6: 保存が進行中でないときに `flush()` を呼ぶと、`save()` がすぐに 1 回だけ呼ばれ、その完了で `flush()` が解決する。
- [ ] AC7: 保存が進行中に予約の時刻が来て追加の保存が決まった後、それが始まる前に `cancel()` を呼ぶと、進行中の保存の完了後に追加の `save()` は呼ばれない。
