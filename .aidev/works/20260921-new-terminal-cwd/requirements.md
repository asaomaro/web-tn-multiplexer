# 要件: 新しい workspace・tab・pane を、いま見ている場所で開く（herdr の `terminal.new_cwd`）

## 背景 / 課題

herdr には、新しい pane・tab・workspace をどこで開くかを決める設定 `terminal.new_cwd` がある
（`herdrdev/herdr` の commit `da6bcd5969779bfe0396bcf89a8025d4375d611e`——`docs/herdr-parity.md:3` が固定している版——の
`docs/next/website/src/content/docs/configuration.mdx:89-94`、`src/config/model.rs:220-226` の `NewTerminalCwdConfig`）。

- `follow`（既定）: **元の pane か workspace の場所を引き継ぐ**。元が無ければ `$HOME`。
- `home`: 常に `$HOME`。
- `current`: herdr を起動した場所。
- 固定のパス（例 `~/Projects`）。
- CLI や API で `--cwd` を明示したときは、そちらが勝つ。

本製品は、この設定が無いうえに、振る舞いも herdr の既定（`follow`）と違う:

- **新しい workspace は（Git worktree を開く操作を除き）いつもサーバを起動した場所で開く**。サーバは `workspace.create` の
  `cwd` を受け付ける（`packages/protocol/src/messages.ts:60-64`・`packages/server/src/session/SessionService.ts:121-122`）が、
  ［＋ 新規］と `prefix+shift+n` の経路は `cwd` を送っていない（`packages/web/src/actions/ActionDispatcher.ts:435-438`）。
  送っているのは worktree を開く経路だけ（同 `:256`）。
- **新しい tab は、その workspace を作ったときの場所で開く**（`SessionService.ts:179` の `ws.cwd`）。
  pane の中で `cd` しても、次に開く tab には引き継がれない。
- 分割した pane は元の pane の記録された場所（`SessionService.ts:245` の `source.cwd`）。この記録は実行中にも書き換わる
  （エージェントの監視が `SessionService.ts:353` の `updatePaneRuntime` へ渡す。`packages/server/src/agent/AgentMonitor.ts:173`・`:190`）が、
  **どの時点で・どの OS で・シェルの `cd` にどれだけ追従しているかは未確認**（research で確かめる）。

その結果、**複数のリポジトリを並行して見張る使い方が塞がれている**（`.aidev/backlog/product-roadmap.md:64`）——
別のリポジトリで作業を始めるたびに、新しい workspace や tab で `cd` し直すことになる。

## 目的 / ゴール

- **pane で別のリポジトリへ移ってから新しい workspace を作ると、そのリポジトリで開く状態**。
- **新しい tab・分割した pane も、いま見ている pane の場所で開き、毎回 `cd` し直さずに済む状態**。
- **決まった場所から始めたい利用者は、その方針（ホーム・起動した場所・指定した場所）を選べる状態**。
- 既存の「場所を明示して開く」操作（Git worktree を開く）は、方針に関わらず今までどおり明示した場所で開く状態。

## ユーザーストーリー

- US1: 複数のリポジトリを並行して見張る利用者として、**pane で別のリポジトリへ移ってから新しい workspace を作ると、
  そのリポジトリで開いてほしい**。なぜなら、いまはいつもサーバの起動場所で開き、別のリポジトリのエージェントを
  見張り始めるたびに `cd` し直すことになるから。（受け入れ: AC1, AC4, AC5）
- US2: 同じリポジトリの中で tab や pane を増やす利用者として、**いま見ている pane の場所で開いてほしい**。
  なぜなら、サブディレクトリで作業しているときに新しい tab がリポジトリの根（や起動場所）で開くと、毎回戻り直すから。
  （受け入れ: AC2, AC3）
- US3: 決まった場所から始めたい利用者として、**新しく開く場所の方針を選びたい**（ホーム・起動した場所・指定した場所）。
  なぜなら、いつも同じ作業場所から始める人にとっては「引き継ぐ」がかえって邪魔になるから。（受け入れ: AC6, AC7, AC8, AC9, AC10）
- US4: Git worktree を開く利用者として、**方針に関わらず worktree の場所で開いてほしい**。
  なぜなら、worktree を開く操作は場所そのものを選ぶ操作だから。（受け入れ: AC11）

## スコープ

### 対象

- 新しい workspace・tab・分割した pane を開く場所の**方針**（herdr の `follow`・`home`・`current`・固定のパスに相当する 4 つ）。
- **既定は「引き継ぐ」**（herdr と同じ）。
- 方針を選ぶ場所（設定画面か、サーバの起動時の指定か——**どこで選ぶかは design で決める**）。
- 引き継ぐ元の場所が分からない・指定した場所が使えないときの扱い。
- `docs/herdr-parity.md` の該当行の更新と、利用者向けの文書。

### 対象外

- **ディレクトリを選ぶ画面**（ファイルブラウザ・パスの補完）。固定のパスは文字で入れる。
- herdr の `terminal.shell_mode`（ログインシェルかどうか）・`default_shell`（本製品は `--shell` で済んでいる。
  `.aidev/works/20260920-agent-notifications/research.md` の F95 で「実装済み」に分類した）。
- 既に開いている pane の場所を変えること。
- サーバの再起動をまたいで、pane の「いまの場所」を復元すること（既存の復元の仕組みは変えない）。

## 機能要件

- 方針が「引き継ぐ」のとき:
  - 新しい workspace は、**いま見ている pane の、いまの場所**で開く。
  - 新しい tab は、**その workspace の中でいま見ている pane の、いまの場所**で開く。
  - 分割した pane は、**分割した元の pane の、いまの場所**で開く。
  - 「いまの場所」は、**シェルで `cd` した後の場所**を指す（pane を作ったときの場所ではない）。
- 方針が「ホーム」「起動した場所」「指定した場所」のとき、上の 3 つはすべてその場所で開く。
- 場所を明示して開く操作（Git worktree を開く）は、方針に関わらず明示した場所で開く。
- **引き継ぐ元の pane の「いまの場所」が分からない**ときは、**その pane の記録された場所**（最後に分かっている場所）で開く。
  **引き継ぐ元の pane が無い**ときは、**以前と同じ場所**で開く（workspace はサーバを起動した場所、tab はその workspace の場所）。
  どちらも利用者の操作の誤りではないので、**知らせない**（design D4・decisions D4）。
- **指定した場所が使えない**（無い・ディレクトリでない・入れない）ときは、**以前と同じ場所**で開き、**使えなかったことを知らせる**
  （利用者が直せる誤りなので）。代わりの場所は上と同じ 1 つにそろえる（design D3・decisions D1）。
- どちらの場合も、**開けなくなることは無い**。

## 非機能要件 / 制約

- 3 つの OS（Linux・macOS・Windows）で動く。「いまの場所」の分かり方は OS で違いうるので、分からない OS でも
  **既定の振る舞いより悪くならない**（少なくとも今と同じ場所で開く）。
- 新しい workspace・tab・pane を開くのを、「いまの場所」を調べるために待たせすぎない。**調べるのにかける時間に上限があり、
  超えたら「いまの場所が分からない」として扱う**（上限の値は design で決める）。
- 既存の操作（`prefix+c`・`prefix+v`/`prefix+-` の分割・サイドバーの［＋ 新規］・worktree を開く）の入口は変えない。

## 完了条件 (受け入れ基準)

- [ ] AC1: 方針が「引き継ぐ」（既定）のとき、pane で別のディレクトリへ `cd` してから新しい workspace を作ると、
      **その `cd` した先**で開く。
- [ ] AC2: 方針が「引き継ぐ」のとき、pane で `cd` してから新しい tab を開くと、**その `cd` した先**で開く。
- [ ] AC3: 方針が「引き継ぐ」のとき、pane で `cd` してから分割すると、新しい pane は**その `cd` した先**で開く。
- [ ] AC4: **何も設定していない利用者**は「引き継ぐ」になっている。
- [ ] AC5: 引き継ぐ元の pane の「いまの場所」が分からないとき（その OS で分からない・pane のプロセスが終わっている・
      調べる時間の上限を超えた等）は、**その pane の記録された場所**で開く。**引き継ぐ元の pane が無い**とき（焦点の pane が決まらない等）
      は、**以前と同じ場所**で開く——workspace はサーバを起動した場所、tab はその workspace の場所。**どちらも知らせない**。
- [ ] AC6: 方針を「ホーム」にすると、新しい workspace・tab・pane はホームディレクトリで開く。
- [ ] AC7: 方針を「起動した場所」にすると、新しい workspace・tab・pane はサーバを起動した場所で開く。
- [ ] AC8: 方針を「指定した場所」にしてパスを入れると、新しい workspace・tab・pane はそのパスで開く（`~` はホームとして扱う）。
- [ ] AC9: 指定した場所が使えない（無い・ディレクトリでない・入れない）ときは、**以前と同じ場所で開き**（AC5 と同じ代わりの場所。
      workspace はサーバを起動した場所）、その場所が使えなかったことを利用者に知らせる。
- [ ] AC10: 方針の選択は、次に開く workspace・tab・pane から効く（既に開いている pane は変えない）。
- [ ] AC11: Git worktree を開く操作は、方針に関わらず worktree の場所で開く。
- [ ] AC12: `docs/herdr-parity.md` の **H36**「新規 pane の既定シェル・起動モード・cwd の方針」（`:61`）のうち、cwd の方針が
      この work の結果に更新されている（シェルと起動モードの部分を済みに見せないよう、行を割るか書き分ける）。
      **この AC はどのストーリーにも紐づかない**（対応表の保守）。
- [ ] AC13: 利用者向けの文書（`docs/verification.md` の手順）に、新しく開く場所の方針と、その確かめ方が書かれている。
      **この AC もストーリーに紐づかない**（文書の保守）。

## 相互作用の受け入れ基準（UI を伴う work のみ）

方針を選ぶ場所が画面（設定）になった場合に適用する（design で決める）。

- [ ] AC-I1 開く / 閉じる: 方針は既存の設定の画面の中で選ぶ（新しい画面を増やさない）。閉じても選んだ結果は残る。
- [ ] AC-I2 確定 / 取り消し: 方針は選んだ時点で効く（確定ボタンを置かない）。**指定した場所のパスは、打ちかけの途中の値で
      開いてしまわない**（入れ終えた時点で効く）。取り消しは選び直す・入れ直すこと。
- [ ] AC-I3 キーボードだけで完結するか: 方針を選ぶ → パスを入れる → 閉じる、がマウス無しで通せる。
- [ ] AC-I4 フォーカスの行き先: 設定の画面の既存の作法どおり（開いたら最初の項目、閉じたら開く前の pane）。
- [ ] AC-I5 既存の操作を妨げないか: パスを入れている間のキー（文字・Esc・Enter）を端末へ漏らさない。

## 未確定事項 / 確認したいこと

- **「いまの場所」をどう知るか**（OS ごと）。Linux は `/proc/<pid>/cwd`、シェルが出す OSC 7 を読む手もある。
  既存の `packages/server/src/platform/LinuxProcessInspector.ts`・`packages/server/src/terminal/Mirror.ts` に手掛かりがありそう。
  → research。
- **方針をどこで選ぶか**。herdr はサーバ側の設定（1 人で使う前提）。本製品は複数のブラウザから繋がるので、
  「ブラウザごとの設定」にするか「サーバの起動時の指定」にするか。ブラウザごとにするなら、tab や分割の要求にも
  方針を載せる必要がある（いまの protocol では tab・分割は場所を受け付けない——research で確かめる）。
- 「いま見ている pane」の定義（複数のブラウザで別の pane を見ている場合、要求を出したブラウザの焦点の pane か）。
- 指定した場所が使えなかったことを、いつ・どう知らせるか（開くたびか、設定したときか）。
