# 要件: キーの設定の使い勝手

紐づく charter ゴール: `.aidev/charter.md` は本リポジトリに無いため対象外。

## 背景 / 課題

20260921-keybinding-customization で節「キー」の割り当て編集が、20260922-keybinding-presets で
プリセット選択ができるようになった。その過程で、実装した本人の視点から次の4つの使い勝手の課題が
見つかり、backlog（`.aidev/backlog/product-roadmap.md` 31 行目）に残されている。

1. 節「キー」は 34 個の `<details>` を上から順に開いて探すしかなく、目的の操作を見つけにくい。
2. 割り当てが衝突したとき（すでに別の操作が使っている chord）、利用者は理由を読んで手動でその
   操作を探し、割り当てを外してから戻ってこないといけない。
3. macOS の非 US 配列（Dvorak・QWERTZ・AZERTY）では、Option の chord の表示が実際に押した字と
   食い違う（`packages/web/src/keys/chord.ts:244-245` に既知の制約として記載済み。動作は正しい
   ——表示だけの問題）。
4. ブラウザ・OS が先に受けて画面に届かないキー（`Ctrl+T`・`Ctrl+N`・`Ctrl+W` 等）は、全画面のとき
   だけ Keyboard Lock API で受け取れる可能性があるが未対応（research F27。実験的 API）。

## 目的 / ゴール

節「キー」で、利用者が目的の操作をすぐ見つけられ、衝突したときにその場で解決でき、macOS の非 US
配列でも表示が実際に押した字と一致し、全画面のときはブラウザ予約キーも割り当てに使える状態
（4 番目は対応ブラウザ・実験的 API という制約つきで、opt-in の状態）。

## ユーザーストーリー

- US1: 節「キー」で特定の操作の割り当てを変えたい利用者として、操作名で絞り込みたい。
  なぜなら、34 個を毎回上から探すのは時間がかかるから。（受け入れ: AC1〜AC3, AC-I1〜AC-I5）
- US2: 割り当てを変えようとして衝突した利用者として、その場で「こちらへ移す」で解決したい。
  なぜなら、いま別の操作が使っている chord を新しい操作へ動かすのに、いったん諦めて古い操作の行を
  探して外し、また新しい操作の行へ戻ってくる手間を省きたいから。（受け入れ: AC4〜AC7, AC-I6〜AC-I10）
- US3: macOS で Dvorak・QWERTZ・AZERTY を使う利用者として、Option の chord の表示を実際に押した字で
  見たい。なぜなら、いまの表示（QWERTY の位置の字）は自分が押した字と違って読みづらいから。
  （受け入れ: AC8〜AC10）
- US4: 全画面で作業する利用者として、ブラウザが先に受けて今まで割り当てられなかったキー
  （`Ctrl+T` 等）も使いたい。なぜなら、prefix なしの直接のキーの選択肢を広げたいから。
  （受け入れ: AC11〜AC14, AC-I11〜AC-I12）

## スコープ

### 対象

- 節「キー」の操作一覧に絞り込み用の入力欄を足す（操作名・群名での部分一致、大小無視）。
- 衝突したときの案内文に「こちらへ移す」ボタンを添え、押すと衝突相手からその chord を外して
  いま入力中の対象へ割り当てる。
- macOS で `navigator.keyboard.getLayoutMap()`（Chromium 系のみ。feature-detect）が使えるとき、
  `alt+…` を含む chord の表示を、いまのキー配列で実際にその物理キーが打つ字に置き換える
  （**表示だけ**。取り込み・照合のロジックは変えない）。
- 全画面（`document.fullscreenElement`）のときだけ、ブラウザ・OS 予約キーの一部
  （research F27 が挙げた `Ctrl+T`・`Ctrl+N`・`Ctrl+W`・`Ctrl+Shift+T/N/W`・`Ctrl+Tab`・
  `Ctrl+PageUp/PageDown`）を `navigator.keyboard.lock()` で受け取れるようにする。**既定は無効**
  （設定で opt-in）。API が無い・失敗する環境では黙って今までどおり（AC14）。

### 対象外

- サーバー・protocol の変更は無い（ブラウザの `wtm.prefs.v1` のみ）。
- 独自コマンドのキー（H12。サーバでコマンドを実行する仕組みが要る。別 backlog 行）。
- navigate モードの移動キー・herdr にあって本製品に操作自体が無いもの（別 backlog 行）。
- 全画面そのものへの入退場 UI（ボタン等）は作らない——ブラウザ既定の全画面操作（F11・全画面
  メニュー等）で `document.fullscreenElement` が変わるのを**受け身で検知するだけ**。
  本製品が `requestFullscreen()` を能動的に呼ぶ導線は作らない（対象外。理由: 全画面ボタンの追加は
  別の UI 変更で、この work の主題〔既存のキー割り当ての使い勝手〕から外れる）。
- Keyboard Lock で受け取れるようにするキーの一覧は research F27 が挙げた範囲に限る。それ以外の
  ブラウザ予約キー（`Alt+Tab` 等 OS レベルのもの・一次資料で確認していないもの）は対象外
  （research F27 の「個々の予約キーの一覧は一次資料で確かめていない」という制約を踏襲）。
- macOS 以外の配列の表示の不一致（もしあれば）は対象外——backlog の記述どおり、macOS の Option
  chord の表示に限る。

## 機能要件

- 絞り込み入力欄は節「キー」の先頭（prefix の行より前、または直後）に置き、入力するたびに
  一覧が絞られる。一致対象は**操作名・群名**（既存の `GROUPS`＝「全体」「workspace / tab」「pane」。
  `packages/web/src/components/KeySettings.vue:35` の表示単位をそのまま使う）。絞り込みで 0 件に
  なった群は見出しごと隠す。空にすると全 34 個に戻る。
- 衝突の案内に「こちらへ移す」ボタンが添う条件：取り込んだ chord が**別の操作の割り当て**である
  場合。移せない（＝衝突の理由が「別の操作の割り当て」以外）ケースは対象外として理由だけ出す
  （AC7）。
- 「こちらへ移す」を押すと、衝突相手からその chord を外し、いま入力中の対象へ割り当てる
  （1 回の操作で完結。確認ダイアログは挟まない——既存の取り込みの流儀〔確定は押した瞬間〕に合わせる）。
- macOS の chord 表示の置き換えは、`getLayoutMap()` が使えないとき・対応する `code` が無いときは
  今までの表示（QWERTY の位置の字）に自動でフォールバックする。
- Keyboard Lock は設定画面に opt-in の switch を持ち、既定は無効。有効かつ全画面のときだけ
  `navigator.keyboard.lock()` を呼び、全画面を抜けたら `unlock()` する。

## 非機能要件 / 制約

- 絞り込み・「こちらへ移す」は既存のキーボードだけでの操作性（AC-I3〜AC-I5 相当）を壊さない。
- `getLayoutMap()`・Keyboard Lock はいずれも実験的 API（Chromium 系限定・セキュアコンテキスト必須。
  2026-09-22 時点で MDN が「Limited availability」「Not Baseline」と明記）。**使えない環境では
  例外を投げず、黙って今までの挙動のまま**にする（feature-detect + try/catch）。
- Keyboard Lock は `navigator.keyboard.lock()` の呼び出しに transient user activation が要る
  （MDN）。全画面への遷移自体が利用者の操作なので、`fullscreenchange` イベント内での呼び出しが
  この条件を満たす前提で設計する（design で実機の挙動が違えば申し送る）。

## 完了条件 (受け入れ基準)

- [ ] AC1: 節「キー」に絞り込み入力欄があり、操作名または群名の一部を入力すると一致する操作だけが
      残る（大小文字を区別しない）。
- [ ] AC2: 一致する操作が 0 個の群（全体・workspace / tab・pane）は見出しごと表示されない。
- [ ] AC3: 入力を空にすると 34 個全部に戻る。
- [ ] AC4: 割り当てを取り込んで衝突した（別の操作がその chord を使っている）とき、案内文に
      「こちらへ移す」ボタンが出る。
- [ ] AC5: 「こちらへ移す」を押すと、衝突相手の割り当てからその chord が外れ、いま入力中の対象へ
      割り当てられる（1 回の操作で完結、確認ダイアログなし）。
- [ ] AC6: 「こちらへ移す」を使わずに終える（Esc・フォーカスを失う・他の操作）と、何も変わらない
      （移動は明示的にボタンを押したときだけ起こる）。
- [ ] AC7: 衝突の理由が「別の操作の割り当てを使っている」以外（prefix そのものと同じ・予約された
      キー・範囲の操作の一部など、移す先の割り当てが単一の操作の単一の chord として特定できない
      場合を含む）のときは「こちらへ移す」を出さない（移す先が存在しない・特定できないため）。
- [ ] AC8: macOS で `getLayoutMap()` が使える環境では、`alt+…` を含む chord の表示が、いまの
      キー配列で実際にその物理キーが打つ字に置き換わる。
- [ ] AC9: `getLayoutMap()` が使えない（非対応ブラウザ・非 macOS・取得失敗）ときは、今までどおり
      QWERTY の位置から復元した字で表示する（回帰なし）。
- [ ] AC10: 表示が変わっても、取り込み・照合・保存される chord の文字列（`alt+w` 等）自体は
      変わらない（表示専用の変換であることをテストで確かめる）。
- [ ] AC11: 設定画面に「全画面のとき、ブラウザ予約キーも使う」旨の switch があり、既定は無効。
- [ ] AC12: 有効にして全画面に入ると、research F27 が挙げた予約キー（`Ctrl+T` 等）が画面に届き、
      割り当てた操作が実行される（またはそのキーへ割り当てられる）。
- [ ] AC13: 全画面を抜けると、そのキーはまたブラウザ・OS が先に受ける（`unlock()` される）。
- [ ] AC14: `navigator.keyboard.lock` が存在しない・呼び出しが失敗する環境では、例外を投げず、
      今までどおり動く（switch 自体は出してよいが、有効にしても効果が無いことが分かる）。

## 相互作用の受け入れ基準

- [ ] AC-I1 開く / 閉じる: 絞り込み入力欄は節「キー」の中の常設の部品で、開閉の概念を持たない
      （フォーカスすればいつでも使える）。
- [ ] AC-I2 確定 / 取り消し: 絞り込みは入力するたびに即時反映（確定操作は無い）。「こちらへ移す」は
      押した瞬間に確定（AC5 と同じ。取り消しは既存の削除操作で行う）。
- [ ] AC-I3 キーボードだけで完結するか: 絞り込み欄へ Tab で入り、文字を打つ→一致した行へ Tab で
      進む、がマウス無しで通る。
- [ ] AC-I4 フォーカスの行き先: 絞り込み欄はフォーカスを保持したまま一覧が変わる（入力のたびに
      フォーカスが奪われない）。
- [ ] AC-I5 既存の操作を妨げないか: 絞り込み欄への入力は、取り込み待ち（`.keys-capture`）の
      `keydown` ハンドラとは独立していて、干渉しない（取り込み待ち中は絞り込み欄を操作できない
      ことは許容する——同時に 2 つの入力状態を持たない設計を踏襲）。
- [ ] AC-I6 開く / 閉じる: 「こちらへ移す」ボタンは衝突が起きたときだけ、案内文の直後に現れる
      （常設ではない）。
- [ ] AC-I7 確定 / 取り消し: AC-I2 と同じ（「こちらへ移す」＝即時確定。他の操作を選べば消える）。
- [ ] AC-I8 キーボードだけで完結するか: 衝突後、Tab で「こちらへ移す」ボタンへ到達し Enter で押せる。
- [ ] AC-I9 フォーカスの行き先: 「こちらへ移す」を押した後のフォーカスの行き先は design で決める
      （既存の「置き換え」操作〔`apply` の `t.replacing` 分岐〕と同じ「新しい割り当ての［変更］へ」
      が候補）。
- [ ] AC-I10 既存の操作を妨げないか: 「こちらへ移す」ボタンの追加は、既存の削除・変更・追加の
      各ボタンの配置とタブ順を崩さない（案内文の直後という新しい部品を足すだけで、既存の部品の
      並びは変えない）。
- [ ] AC-I11 全画面の switch の効果が分かるか: 有効にしても全画面でなければ何も起きない（悪影響も
      無い）ことが、設定画面の説明文から分かる。
- [ ] AC-I12 既存の操作を妨げないか: Keyboard Lock は既存の直接のキー・prefix の判定ロジックを
      変えない（ブラウザが届けるキーが増えるだけで、届いたキーの扱いは今までと同じ経路を通る）。

## 未確定事項 / 確認したいこと

- 「こちらへ移す」を押した後のフォーカスの行き先の具体（AC-I9）→ design で決める。
- 絞り込み入力欄の設置位置（節「キー」の中で prefix の行より前か直後か。機能要件は両案を並べた
  まま）→ design で決める。
- Keyboard Lock の呼び出しタイミング（`fullscreenchange` イベント内で直接か、ユーザーの明示操作を
  介するか）が transient user activation の条件を満たすかは、一次資料だけでは確定できないため、
  design で実装しつつ確認し、実機検証（`docs/verification.md`）に申し送る。
